# 3.2 — Disk-backed buffering for large PDFs (`buffering.mode`)

Issue: [#178](https://github.com/intoolswetrust/jsignpdf/issues/178) — "Signing large PDFs" (up to 1 GB,
without loading the whole document into memory).

## Goal

Give users an opt-in mode that moves the signing intermediates from the Java heap to temporary files, so
document size stops being bounded by `-Xmx`. **Default behaviour does not change**: both engines keep
buffering in memory exactly as today, byte-for-byte.

Non-goals: streaming/chunked PDF rewriting (neither OpenPDF nor DSS supports it), reducing the parsed
object model's footprint, and any GUI surface (see §"Deliberately out of scope").

## Current state — where the memory goes

**OpenPDF engine.**

*Reading* is partly lazy. `new PdfReader(String)` → `PRTokeniser` → `RandomAccessFileOrArray` with
`Document.plainRandomAccess == false`, i.e. a `MappedRandomAccessFile`; the mapping is off-heap, so the raw
file bytes do not count against `-Xmx`. But `readPdf()` → `readDocObj()` (`PdfReader.java:1918`)
materialises **every** indirect object into the `xrefObj` list eagerly. Only stream *payloads* stay on
disk — a `PRStream` holds a file offset and is re-read on demand through `getSafeFile()`. So the object
model (dictionaries, arrays, xref-stream contents) is fully heap-resident before signing starts, and this
mode does not change that.

*Writing* is not lazy at all. `OpenPdfSigningEngine.java:193` calls

```java
PdfStamper.createSignature(reader, fout, tmpPdfVersion, null, options.isAppendX());
```

The 4th argument is a temp `File`; `null` selects OpenPDF's in-heap branch — `PdfStamper` allocates a
`ByteBuffer`, and `PdfSignatureAppearance.preClose()` takes `bout = sigout.getBuffer()`, so the complete
signed document lives in one heap `byte[]`. `getRangeStream()` then digests out of that array, and
`close()` copies it to `originalout`.

Two consequences:

- peak heap ≈ full output document + parsed object model + decompressed object streams;
- **a 2 GB ceiling on the staged output** regardless of `-Xmx`, because the buffer is an int-indexed array —
  in-memory mode even does `System.arraycopy(..., (int) byteRangePosition, ...)`.

**DSS engine.** Three separate buffers, only one of which the DSS factory setting reaches:

- `new FileDocument(effectiveInFile)` at `DssSigningEngine.java:287` is fine (PDFBox 3 reads lazily), but
  `signWithContentSize()` returns an in-memory `DSSDocument` that is only then streamed out
  (`signedDocument.writeTo(fos)`). DSS's default `PAdESUtils.DEFAULT_RESOURCES_HANDLER_BUILDER` is the
  in-memory one. The undersize-retry loop can re-run the whole operation, so the transient peak repeats.
- `configureVisibleSignature()` (`:633`) calls `Loader.loadPDF(inFile)` just to read a page's MediaBox.
- `encryptPdf()` (`:588`) calls `Loader.loadPDF(inFile)`, re-encrypts and `doc.save(tempFile)`.

The two `Loader.loadPDF(File)` calls use PDFBox 3's default **memory-only** stream cache. They are outside
DSS entirely, so `IPdfObjFactory.setPdfMemoryUsageSetting(...)` does not affect them — see §"DSS engine".

**Heap available.** No `-Xmx` in `distribution/jpackage/common-jvm-options.txt`, so launchers get the JVM
default of ¼ of physical RAM. `OpenPdfSigningEngine.java:442` catches `OutOfMemoryError` and prints
`console.memoryError`; `website/docs/JSignPdf.adoc:1188` documents raising the heap.

## The library support already exists

Nothing needs to be invented — all three stacks ship a supported disk-backed mode:

| | in-memory (today) | disk-backed (opt-in) |
|---|---|---|
| OpenPDF | `createSignature(..., tempFile = null, ...)` | pass a real `File`; `PdfSignatureAppearance` then seeks/writes through a `RandomAccessFile` (`raf`) with **long** offsets |
| DSS output | `PAdESUtils.DEFAULT_RESOURCES_HANDLER_BUILDER` | `IPdfObjFactory.setResourcesHandlerBuilder(new TempFileResourcesHandlerBuilder())` |
| DSS/PDFBox parsing | `PdfMemoryUsageSetting.memoryFull()` (DSS default) | `IPdfObjFactory.setPdfMemoryUsageSetting(PdfMemoryUsageSetting.mixed(n))` / `.fileOnly()` |
| direct PDFBox loads in the DSS engine | `Loader.loadPDF(file)` | `Loader.loadPDF(file, streamCache)` with `MemoryUsageSetting.setupMixed(n).setTempDir(dir).streamCache` |

`JSignPdfPdfObjFactory` (extending `AbstractPdfObjFactory`) is already constructed and installed at
`DssSigningEngine.java:324-334`, and `AbstractPdfObjFactory` exposes both setters
(`AbstractPdfObjFactory.java:71`, `:96`) — so the DSS factory side is configuration, not new plumbing.

## Setting

One engine-agnostic key in `advanced.properties`, because it is a property of the machine/workload, not of
the signing algorithm. The key names the *buffering strategy*, not the file — `largeFile.*` was rejected
because the knob is about where intermediates live, and a user-facing key cannot be renamed later.

```properties
# How the signing intermediates are buffered.
#   memory (default) - everything on the Java heap; fastest, bounded by -Xmx and
#                      by a 2 GB staged-output limit in the openpdf engine.
#   temp             - intermediates go to temporary files; needed for very large
#                      documents, costs disk I/O and free space (see the docs for
#                      the per-engine multiple of the document size).
buffering.mode=memory

# Directory for those temporary files. Empty = java.io.tmpdir. Point this at a
# fast local disk with enough free space when signing very large documents. It
# must already exist and be writable; JSignPdf does not create it.
buffering.tempDir=
```

An enum (not a boolean) so `mixed`/`fileOnly` tuning can be added later without a second key. Unknown value
→ log a warning and fall back to `memory`.

Reachable through every existing channel with no extra work: `advanced.properties`, the CLI
`-o buffering.mode=temp` override (see `3.1-advanced-overrides.md`), and the config-dir layering.

### Plumbing

`EngineConfig` is scoped to `engine.<id>.*` and cannot read a global key. The precedent for a global key
consumed inside an engine module already exists: `DssFontUtils.java:37` reads `AppConfig.fontPath()`
directly. Follow it.

- **Recommended:** add `AppConfig.bufferingMode()` and `AppConfig.bufferingTempDir()` next to the existing
  accessors in `engines/api/.../utils/AppConfig.java`, and call them from both engines. No SPI change, no
  `EngineConfig` change, no new value object.
- **Not** "resolve the global keys into the engine-scoped namespace when `AdvancedEngineConfig` is built":
  `AdvancedEngineConfig` (`:26-38`) is a pure prefix wrapper over `AdvancedConfig` with no injection point,
  so that phrasing does not describe an implementable change.
- Per-engine override (`engine.dss.buffering.mode`) is **not** part of this change — decided, not blocked.
  It would be cheap (resolve `engine.<id>.buffering.mode` then `buffering.mode` inside `AppConfig`, leaving
  `AdvancedEngineConfig` and every other engine key untouched), but nobody has asked for it and the mode is
  a property of the machine and workload, which does not vary by engine. One key, one meaning. The enum
  leaves room to add the override later without breaking anything.

`AppConfig.bufferingTempDir()` returns the validated directory or `null`:

- empty/unset → `null` (use `java.io.tmpdir`);
- set → must exist, be a directory, and be writable. Otherwise log an error and **fail the sign**.

The key is only read when `bufferingMode == TEMP`. In `memory` mode it is inert, so a stale or removed path
left in someone's `advanced.properties` must not break a sign that never touches it. Validate in one shared
place rather than per engine, because the engines disagree on their own: `File.createTempFile(..., dir)`
throws for a missing directory, while `TempFileResourcesHandlerBuilder.createResourcesHandler()`
(`TempFileResourcesHandlerBuilder.java:116-127`) silently `mkdirs()` it.

## Implementation

### Non-issue — the unclosed `PdfReader` (investigated, nothing to fix)

An earlier draft called for adding `reader.close()` to `OpenPdfSigningEngine`, on the theory that the
memory-mapped input stays mapped for the process lifetime. **That is wrong; do not implement it.**

- `PdfReader.readPdf()` closes the tokeniser in its own `finally`, and `MappedRandomAccessFile.close()`
  (`:202-208`) nulls the buffer and closes the `FileChannel`. The mapping is released before the
  constructor returns; later stream reads reopen the file on demand through `getSafeFile()` and close it
  again.
- `PdfReader.close()` (`:3411-3414`) is `if (!partial) return;`. JSignPdf uses the non-partial
  constructor, so the call would be a no-op.

Verified empirically: a test asserting zero open descriptors on the input after signing, and that the input
is deletable, passes identically with and without the added `close()`. Recorded here so the idea is not
re-proposed.

### OpenPDF engine — `OpenPdfSigningEngine.sign()`

Create the temp file in JSignPdf, not by handing OpenPDF a directory. `createSignature` *will* create one
itself when passed a directory, but it never returns the name, and **OpenPDF only deletes it in
`close()`** (`PdfSignatureAppearance.java:1382-1391`) and on a `preClose` `IOException` (`:1302-1306`) — so
an abort between `preClose()` and `close()`, which is exactly where TSA/OCSP/network failures live, leaks a
file the size of the document. Owning the `File` lets the engine delete it in its own `finally`.

```java
File sigTempFile = null;
if (bufferingMode == TEMP) {
    sigTempFile = File.createTempFile("jsignpdf-sig-", ".pdf", tempDirOrNull);
    sigTempFile.deleteOnExit();
}
final PdfStamper stp = PdfStamper.createSignature(reader, fout, tmpPdfVersion, sigTempFile,
        options.isAppendX());
...
// existing finally block, next to the fout close
if (sigTempFile != null) {
    sigTempFile.delete();  // no-op when OpenPDF already removed it
}
```

Mirrors the `encryptedTempFile` idiom already in `DssSigningEngine.java:189/271/383`. Nothing else in the
engine changes — `sap.preClose()`, `getRangeStream()` and `sap.close()` all switch to the `raf` path inside
OpenPDF.

### DSS engine — `DssSigningEngine.sign()`

Three call sites, all gated on `bufferingMode == TEMP`.

**1. The signing service factory** (at the existing factory setup, `:324-334`):

```java
TempFileResourcesHandlerBuilder resourcesHandlerBuilder = null;
if (bufferingMode == TEMP) {
    resourcesHandlerBuilder = new TempFileResourcesHandlerBuilder();
    resourcesHandlerBuilder.setFileNamePrefix("jsignpdf-dss-");
    if (tempDirOrNull != null) {
        resourcesHandlerBuilder.setTempFileDirectory(tempDirOrNull);
    }
    pdfObjFactory.setResourcesHandlerBuilder(resourcesHandlerBuilder);
    pdfObjFactory.setPdfMemoryUsageSetting(PdfMemoryUsageSetting.mixed(MIXED_THRESHOLD_BYTES));
}
```

Class lives in `dss-document`: `eu.europa.esig.dss.signature.resources.TempFileResourcesHandlerBuilder`.

Keep the builder a **local variable**, as above. It must not become a field or a static: `clear()` deletes
every temp file the builder ever created, so a shared builder would let one sign delete another concurrent
sign's output document.

**2. The retry loop** — `signWithContentSize()` (`:430-457`) calls `getDataToSign()` **and**
`signDocument()` on every attempt, and every call adds a handler to the builder's internal list that only
`clear()` drains. With `MAX_CONTENT_SIZE_RETRIES = 3` that is up to 8 full-size temp files alive at once on
a 1 GB document. Release them per failed attempt:

Pass the builder into `signWithContentSize` as an extra nullable parameter — it is currently a private
helper with no access to it. The helper is already DSS-specific (it takes `PAdESService`, `ToBeSigned`,
`SignatureValue`), so there is no abstraction worth protecting with an indirection.

```java
private DSSDocument signWithContentSize(PAdESService service, DSSDocument document,
        PAdESSignatureParameters parameters, PrivateKeySignatureToken token, DigestAlgorithm digestAlgorithm,
        int initialContentSize, boolean retryOnUndersize, TempFileResourcesHandlerBuilder builder) {
    ...
    } catch (IllegalArgumentException e) {
        ...
        if (builder != null) {
            builder.clear();  // nothing survivable exists on a failed attempt
        }
        contentSize = grown;
    }
}
```

The **final** `clear()` still belongs in `sign()`'s `finally`, next to the existing
`encryptedTempFile.delete()` at `:383`, because the successful `signedDocument` is a `FileDocument` backed
by one of those temp files and must survive until `signedDocument.writeTo(fos)` has run.

**3. The two direct PDFBox loads.** `Loader.loadPDF(File)` defaults to a memory-only stream cache and is
not reached by `setPdfMemoryUsageSetting`, so without this a 1 GB input is fully buffered on the heap
*before* DSS is involved. `configureVisibleSignature()` runs for every visible signature, which makes it
the largest single hole for #178 on this engine.

```java
// helper in the engine
private static StreamCacheCreateFunction streamCache() {
    if (bufferingMode != TEMP) {
        return null;
    }
    MemoryUsageSetting mus = MemoryUsageSetting.setupMixed(MIXED_THRESHOLD_BYTES);
    if (tempDirOrNull != null) {
        mus.setTempDir(tempDirOrNull);
    }
    return mus.streamCache;
}
```

Then `Loader.loadPDF(inFile)` → `Loader.loadPDF(inFile, streamCache())` at `:588` and `:633`, with the
`null` case falling back to the existing single-arg overload. (`MemoryUsageSetting.streamCache` is a
`public final` field and `setTempDir` returns `this`; confirm at implementation time that the cache
function reads `tempDir` lazily rather than capturing it at construction.)

`encryptPdf()`'s own temp also ignores the setting today:

```java
final File tempFile = File.createTempFile("jsignpdf-dss-enc-", ".pdf");
```

Pass `tempDirOrNull` as the third argument so the encrypt-then-sign path does not write a full copy of the
document to `java.io.tmpdir` regardless of `buffering.tempDir`.

**`MIXED_THRESHOLD_BYTES`**: a private constant (suggest 64 MB). `mixed(n)` keeps small documents in memory
and only spills beyond `n`, which avoids penalising the common case if a user leaves the mode on
permanently. It is a **per-document** budget, not a global one, and `mixed(n)` delegates to `mixed(n, -1)`
— the disk side is unrestricted. `fileOnly()` is the more aggressive alternative; not needed for #178.

## Testing

1. **Regression, default mode** — existing engine tests must pass untouched; assert the default really is
   `memory` (a bug that silently flips it would be invisible in output bytes).
2. **Equivalence** — the core correctness claim: the mode only changes *where* bytes are staged, never what
   they are.

   A plain byte-identity assertion is not available. The signing time is taken from `Calendar.getInstance()`
   inside `PdfSignatureAppearance.getSignDateNullSafe()`; `OpenPdfSigningEngine` never calls the existing
   `setSignDate()`, and there is no clock seam in `SigningTestBase`. That time lands in `/M`
   (`OpenPdfSigningEngine.java:347`) and, for visible signatures, in the L2 text (`:291`) — both **inside**
   the ByteRange-covered region, so restricting the comparison to that region does not help either. The
   signature blob itself is additionally nondeterministic for ECDSA and RSASSA-PSS.

   **A byte-level differential ("diff two memory runs, assert temp differs only there") does not work** —
   it was tried and is unsound. The per-run values drag the CMS message digest with them, so a large part
   of `/Contents` is high-entropy; individual bytes inside it collide between two memory runs often enough
   (~1 in 256) to look "stable", and the same bytes then differ against the temp run. The comparison has to
   be at *region* granularity, not byte granularity.

   What works: normalise the two known per-run values and compare everything the ByteRange covers.

   ```java
   // per-run values, both inside the covered region
   /M (D:\d{14}          -> fixed        // signature dictionary signing time
   /ID [<hex><hex>]      -> fixed        // trailer document ID, regenerated on every save

   assertEquals(memory.length, temp.length);
   assertArrayEquals(memoryByteRange, tempByteRange);   // layout, offsets, /Contents size
   assertArrayEquals(normalise(memory, before), normalise(temp, before));
   assertArrayEquals(normalise(memory, after),  normalise(temp, after));
   ```

   The excluded `/Contents` gap is exactly what the ByteRange already identifies, and it necessarily changes
   when `/M` does. Include a **control**: two memory-mode runs must agree under the same normalisation. If
   the masking is ever incomplete the control fails first and says so, instead of the real assertion failing
   and looking like a staging bug.
3. **Large-file smoke, not in CI** — a generated ~600 MB PDF under a deliberately small `-Xmx` (e.g. 512m):
   fails with `OutOfMemoryError` in `memory` mode, succeeds in `temp`. Keep it as a manually-run
   `@Disabled`/tagged test or a script under `design-doc/`; it is too slow and disk-hungry for CI. Run the
   DSS half **with a visible signature**, since that is the path that exercises fix (3).
4. **Temp-file hygiene** — after a *failed* sign (bad TSA URL is the easiest trigger, since it aborts
   between `preClose` and `close`), assert no `jsignpdf-sig-*` / `jsignpdf-dss-*` / `jsignpdf-dss-enc-*`
   files remain in the temp dir. This is the case OpenPDF itself gets wrong and the reason we own the
   `File`.
5. **Retry-loop hygiene** — force at least one undersize retry (a deliberately small
   `engine.dss.contentSize` with `retryOnUndersize=true`).

   Asserting the staging directory is empty *afterwards* does **not** test this: the engine's final
   `clear()` removes accumulated files too, so the assertion passes with or without the per-attempt
   release. Measured peak concurrent staged files: **2 with** the per-attempt `clear()`, **3 without**. The
   peak has to be sampled during the sign. Make the sampler one-sided — missing the peak under-reports and
   passes, so it can miss a regression but never fails spuriously.
6. **Append mode + visible signature** in `temp` mode, both engines — those paths touch the appearance
   stream and are the most likely to differ.
7. **Custom `buffering.tempDir`** — a valid directory is honoured by both engines; a non-existent and a
   non-writable one produce the same clear error from the shared validation on both engines, with no silent
   fallback to `java.io.tmpdir` and no `mkdirs()`. Plus the inverse: an unusable `buffering.tempDir` with
   `buffering.mode=memory` must **not** fail the sign, since the key is never read in that mode.

## Documentation

- `advanced.default.properties` — both keys with the comment block from §"Setting" (that file is the
  user-facing reference for advanced keys).
- `website/docs/JSignPdf.adoc` — extend the existing "Out of memory error" section (`:1188`) so it offers
  `buffering.mode=temp` *before* raising `-Xmx`, and note the openpdf staged-output limit that `-Xmx`
  cannot fix.
- **Free-space requirement, per engine** — not simply "≥ output size":
  - openpdf: ~1× the output size (one staged copy), plus the output file itself.
  - dss: ~2× the output size per attempt (`getDataToSign` and `signDocument` each stage a full copy), plus
    another 1× while the encrypt-before-sign temp exists. Retries are freed as they fail (fix 2), so the
    peak does not grow with the retry count.
- State that `temp` is slower.
- Note that if the disk fills mid-sign, both a partial temp file and a partial output file can be left
  behind; the temp is cleaned up by the `finally`, the partial output is not (pre-existing behaviour, made
  more likely by this mode).

## Deliberately out of scope

- **GUI.** No Preferences control. Precedent: `engine.dss.contentSize` and `engine.dss.retryOnUndersize` are
  file/`-o` knobs with no GUI binding, and `PreferencesViewModel` is hand-wired per key. GUI users can still
  set the key by editing `advanced.properties`. Add a control later if users ask.
- **Auto-detection** (switch to `temp` when input size > some fraction of `Runtime.maxMemory()`). Tempting,
  and it would fix #178 for users who never read the docs — but it makes the default path
  environment-dependent and the mode is not output-neutral in *performance*. Revisit once `temp` has real
  mileage; the enum leaves room for a `buffering.mode=auto` value.
- **Shipping a default `-Xmx`** in the launchers. Independent decision; the JVM default of ¼ RAM is
  reasonable and pinning a number would *lower* it on big machines.
- **Per-engine override** of the two keys (`engine.<id>.buffering.*`) — cheap to add, but no demand and no
  reason the machine's staging strategy should vary by engine. See §"Plumbing".

## Expected outcome for #178

With `buffering.mode=temp`, a 1 GB PDF becomes limited by disk rather than heap, on both engines. What does
**not** change:

- The **parsed object model** and any decompressed object streams still live on the heap on both engines, so
  a pathological 1 GB document — hundreds of thousands of objects, huge cross-reference tables — can still
  need a large heap.
- The openpdf engine keeps a **hard ~2 GB limit on the input file**, independent of this setting.
  `PdfReader.xref` is an `int[]` (`PdfReader.java:108`), and `RandomAccessFileOrArray.seek(long)` truncates
  to `int` (`seek((int) pos)`), as do `length()` and `getFilePointer()`. Only the *staged output* buffer
  loses its 2 GB ceiling here, because `PdfSignatureAppearance`'s `raf` seeks are `long` and
  `PdfWriter.PdfCrossReference.offset` is `long` (the classic xref's 10-digit offset field tops out near
  9 GB). 1 GB, the size #178 asks for, is comfortably inside the reader limit; larger inputs need the dss
  engine.

The honest claim is "file size no longer drives heap usage, up to 2 GB on openpdf", not "constant memory".
