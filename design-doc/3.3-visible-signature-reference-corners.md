# JSignPdf 3.3 — Configurable Reference Corner for Visible Signatures

**Status:** Draft — design only (no functional implementation)  
**Related issue:** [#533](https://github.com/intoolswetrust/jsignpdf/issues/533)  
**Scope:** JavaFX GUI, CLI, presets, and visible-signature positioning

## 1. Goal

Keep the **physical size** of a visible-signature rectangle and its **offset from a chosen PDF page corner** constant across page sizes (A4, A3, A2, etc.). The user should not need to reposition a signature when switching document formats. The PDF signing engines continue to receive the existing absolute rectangle coordinates (LLX, LLY, URX, URY).

## 2. Terminology

- **PRC — Page Reference Corner:** the user-selected corner of the page, used as a coordinate origin.
- **SAC — Signature Anchor Corner:** the corresponding corner of the signature rectangle, determined automatically from PRC.
- **Reference Offset:** the signed vector from PRC to SAC, `(dx, dy)`.

| PRC | Page origin | Corresponding SAC |
| --- | --- | --- |
| `LL` — Lower Left | `(0, 0)` | `(LLX, LLY)` |
| `LR` — Lower Right | `(W, 0)` | `(URX, LLY)` |
| `UR` — Upper Right | `(W, H)` | `(URX, URY)` |
| `UL` — Upper Left | `(0, H)` | `(LLX, URY)` |

`W` and `H` denote the effective PDF page dimensions in points, in the existing coordinate system. The implementation must respect the page bounds already used by JSignPdf; the table assumes a page origin of `(0, 0)` for clarity. The user selects **only PRC**; SAC is not a separate setting.

## 3. Geometry and calculation order

The canonical geometry is:

`(PRC, dx, dy, width, height)`

where `width = URX - LLX`, `height = URY - LLY`, and

`(dx, dy) = SAC - PRC`.

**When a corner is selected for an already placed signature:**

1. Use the unchanged baseline rectangle in absolute PDF coordinates.
2. Determine the new PRC from the current page dimensions.
3. Select its corresponding SAC from the existing signature rectangle.
4. Calculate `(dx, dy) = SAC - PRC`; retain `width` and `height`.
5. Update the displayed/reference values **without moving or resizing the rectangle**.

**When applying that configuration to a different page:**

1. Determine PRC on the target page.
2. Reconstruct `SAC = PRC + (dx, dy)`.
3. Reconstruct the absolute rectangle using SAC and the unchanged dimensions:

| PRC / SAC | LLX | LLY | URX | URY |
| --- | --- | --- | --- | --- |
| `LL` | `SACx` | `SACy` | `SACx + width` | `SACy + height` |
| `LR` | `SACx - width` | `SACy` | `SACx` | `SACy + height` |
| `UR` | `SACx - width` | `SACy - height` | `SACx` | `SACy` |
| `UL` | `SACx` | `SACy - height` | `SACx + width` | `SACy` |

For example, on a 595 × 842 pt page, a 150 × 60 pt signature at `(LLX, LLY, URX, URY) = (425, 30, 575, 90)` has `PRC = LR`, `SAC = (575, 30)`, and `(dx, dy) = (-20, 30)`. On a page 842 pt wide, it is reconstructed at `(672, 30, 822, 90)` without changing its size or its distance to the right and bottom edges.

## 4. Numerical stability

- Keep a **stable baseline geometry**; switching PRC must not overwrite it or use the previous transformation result as the next input.
- Derive every corner change from the baseline, with `double` precision for intermediate calculations and **no intermediate rounding**.
- Establish a new baseline only after an explicit move/resize or another deliberate geometry edit. Saving a changed PRC serializes the derived configuration without repeated conversion chains.
- Convert to the coordinate types required by the existing signing engine only at its boundary.

Repeated cycles such as `LL → LR → UR → UL → LL` must not cause cumulative positional or dimensional drift.

## 5. Proposed JavaFX GUI

Add a compact **Page Reference Corner** dropdown in the existing **Signature Appearance** section, directly below the **Visible signature** control:

`LL — Lower Left (default) | LR — Lower Right | UR — Upper Right | UL — Upper Left`

Changing the dropdown with a placed rectangle updates only the reference representation, **not the visible placement**. The current JavaFX UI positions the rectangle on the PDF preview rather than exposing four numeric coordinate fields. The exact UI placement is offered for Josef's review.

## 6. Proposed CLI

Add:

`--reference-corner LL|LR|UR|UL`

**Preferred approach:** reuse the existing four rectangle-coordinate arguments, with the following explicit semantics:

- **Without** `--reference-corner`, retain the entire existing CLI behavior, including any established handling of negative coordinates.
- **With** `--reference-corner`, interpret the four numbers as coordinates of the rectangle in the **PRC-relative coordinate system**. First select the SAC appropriate to PRC, then derive its offset and the rectangle dimensions, then reconstruct the absolute PDF rectangle for the target page.
- In this relative system, coordinates left of the chosen origin and below it are negative. For example, with `LR`, the local rectangle `(-170, 30, -20, 90)` describes a 150 × 60 pt signature 20 pt from the right and 30 pt from the bottom.

This avoids introducing four additional coordinate arguments. **Josef's review is requested** on whether reusing the current CLI arguments is preferable to explicit offset/size arguments, particularly given legacy negative-coordinate conventions.

## 7. Presets and compatibility

- **Legacy preset (no `referenceCorner` property):** treat as `LL` and preserve the original stored rectangle and its behavior exactly. Loading it does not rewrite the preset.
- **Newly saved preset:** store `referenceCorner` explicitly and sufficient signed offset and size data to reconstruct `(PRC, dx, dy, width, height)` on different page sizes. The exact property names and encoding should follow JSignPdf's existing preset conventions.
- When loading a legacy preset, selecting a different PRC recalculates the reference values without moving its rectangle. A subsequent save can produce the new representation.
- No separate preset format-version field is proposed solely for this feature.

## 8. Constraints / out of scope

- Do not alter the internal PDF signing coordinate system or the cryptographic signing engines.
- Do not change the location defined by an existing PDF signature field.
- Do not automatically move, resize, or scale a rectangle that falls outside the page; preserve existing placement/validation behavior, with **no new modal warning**.
- Do not introduce page-rotation functionality or change the current handling of rotated pages.

## 9. Planned tests

1. All four PRC/SAC mappings and inverse transformations, including signed decimal coordinates.
2. Repeated corner changes without drift or change to the on-screen rectangle.
3. Constant physical size and reference offsets across A4/A3/A2 and different orientations of otherwise unrotated pages.
4. Loading and re-saving legacy presets; saving/loading new presets.
5. CLI behavior with and without the new option, especially legacy negative-coordinate semantics.
6. Rectangle outside the target page: no silent modification; existing validation behavior remains.
7. Existing PDF signature fields remain unaffected.
