# Algorithm agility — RSASSA-PSS, non-RSA keys, TSA nonce

| Issue | Ask | Outcome |
|---|---|---|
| [#255](https://github.com/intoolswetrust/jsignpdf/issues/255) | Sign with RSASSA-PSS | New `--signature-algorithm` option; PSS on the `dss` engine, capability-gated |
| [#23](https://github.com/intoolswetrust/jsignpdf/issues/23) | EC / non-RSA private keys fail | Already fixed by OpenPDF 3; this design adds the evidence to close it |
| [#33](https://github.com/intoolswetrust/jsignpdf/issues/33) | RFC 3161 TSA nonce | One line on the `dss` engine (`openpdf` already sends one), plus an opt-out |

Versions verified against: OpenPDF 3.0.5, DSS 6.4, JDK 21.

## Premises (verified, correct the issue review)

- **The `"RSA"` string is CloudFoxy-only.** `OpenPdfSigningEngine.java:435` (not
  `SignerLogic.java:411`) sits in the external-signing branch; every other path
  calls `sgn.update(...)` on a `Signature` that `PdfPKCS7` built from the key.
- **OpenPDF derives the algorithm from the key.** `PdfPKCS7.java:537-548` maps
  `privKey.getAlgorithm()` → RSA / DSA / EC / ML-DSA OID, else throws
  `unknown.key.algorithm.1`; `:1209` builds `getHashAlgorithm() + "with" + dea`.
  The `"Private keys must be instance of RSAPrivate(Crt)Key"` message of **#23**
  is gone from 3.0.5. **#23 is a verification task.**
- **The nonce gap is on DSS, not OpenPDF.** `TSAClientBouncyCastle.java:196`
  always sends one and `:211` validates the echo. `DssSigningEngine.buildTspSource()`
  (582-608) never calls `setNonceSource`, and `OnlineTSPSource:168` omits the
  nonce unless one is set.
- **OpenPDF cannot do PSS.** No `1.2.840.113549.1.1.10` branch, JCE name is
  always `SHAxxxwithRSA`-shaped, and the SignerInfo writer (`:1416`) emits a bare
  `AlgorithmIdentifier` + `DERNull` with no room for `RSASSA-PSS-params`. Two
  mapping sites would need patching upstream (`:537` and the external-digest copy
  at `:1297`).
- **DSS has PSS first-class**: `EncryptionAlgorithm.RSASSA_PSS` (name literally
  `"RSASSA-PSS"`, OID `1.2.840.113549.1.1.10`), `RSA_SSA_PSS_SHA{256,384,512}_MGF1`,
  `setEncryptionAlgorithm(...)`.

### What DSS already does for us

- `AbstractSignatureTokenConnection.sign(ToBeSigned, SignatureAlgorithm, keyEntry)`
  already builds the PSS parameters: `createPSSParam(digest)` →
  `new PSSParameterSpec(name, "MGF1", new MGF1ParameterSpec(name), digest.getSaltLength(), 1)`,
  applied via `setParameter` before `initSign`. Hand-writing this is redundant.
- JSignPdf's `PrivateKeySignatureToken` extends that class but **overrides the
  digest-only `sign(...)` overload**, bypassing all of it. That override is the
  actual gap, not a missing feature in DSS.
- `AbstractSignatureParameters.setSigningCertificate(...)` **overwrites**
  `encryptionAlgorithm` from the certificate's public key. Any
  `setEncryptionAlgorithm` must come *after* it (DSS documents this).
- `PAdESService.signDocument:207` → `ensureSignatureValue(parameters.getSignatureAlgorithm(), value)`
  throws unless the token's algorithm matches the parameters exactly (only ECDSA
  gets equivalence leeway). Parameters and token must be driven from one value.
- `EncryptionAlgorithm.isEquivalent()` treats the whole RSA family as equivalent,
  so DSS's own `assertEncryptionAlgorithmValid` permits PSS with an
  `rsaEncryption` key — that is what makes the escape hatch in §2 implementable.

### Blocker: PSS JCE naming and provider selection

- `SignatureAlgorithm.getJCEId()` for PSS is `SHA256withRSAandMGF1` — a
  **BouncyCastle-only** service name. `SunRsaSign` / `SunPKCS11` expose PSS as
  `RSASSA-PSS` + `PSSParameterSpec`.
- **Delayed provider selection does not save us.** `Signature$Delegate.engineSetParameter`
  calls `chooseFirstProvider()`, so `setParameter` before `initSign` locks in the
  first provider offering the service. Measured on JDK 21.0.10 with a dummy
  provider inserted at position 1 that rejects the key:

  ```
  setParameter-first: FAILED java.security.InvalidKeyException: BadFirst refuses this key
  initSign-first:     OK provider=SunRsaSign
  ```

- JSignPdf appends BC (`KeyStoreUtils.java:54`) and the PKCS#11 provider
  (`PKCS11Utils.java:124`) via `addProvider`, so a no-provider
  `getInstance("RSASSA-PSS")` resolves to `SunRsaSign`, which cannot take a
  non-extractable `P11Key`. Reordering to `initSign`-first is not a fix either:
  SunPKCS11's PSS SPI rejects `setParameter` after init.
- **Therefore: select the provider explicitly from the key material** (§5).

## Goals / non-goals

Goals:

- Standards-conformant PSS on the `dss` engine, software keystores *and* PKCS#11.
- No user input in the common case: a PSS-only certificate just works.
- Explicit escape hatch where detection cannot see.
- RFC 3161 nonce on both engines by default.
- Close #23 with test evidence.
- No DSS/OpenPDF type leaks into `net.sf.jsignpdf.types.*`.

Non-goals:

- PSS on `openpdf` — capability-gated instead (see "Rejected alternatives").
- EdDSA / ML-DSA — cheap follow-ups (plumbing exists on both sides), no demand,
  thin PAdES validator support. The enum is open for them.
- Changing the default padding — plain RSA certs keep producing PKCS#1 v1.5.
- A GUI picker beyond one combo box next to the hash selector.
- Algorithm negotiation with the TSA (we only control the imprint digest).

## Design

### 0. Probe — DONE, results below

`PssProbeTest` (engines/dss) signs a PDF with three key/certificate shapes on the
current code, no production changes:

| Shape | `key.getAlgorithm()` | cert SPKI | Result |
|---|---|---|---|
| 1. PSS key + PSS cert | `RSASSA-PSS` | `RSASSA-PSS` | **works today** — SignerInfo OID `1.2.840.113549.1.1.10` |
| 2. RSA key + PSS cert (PKCS#11 shape) | `RSA` | `RSASSA-PSS` | **fails** — see below |
| 3. RSA key + RSA cert | `RSA` | `RSA` | works, OID `1.2.840.113549.1.1.11` |

Shape 2 failure:

```
DSSException: The SignatureAlgorithm within the SignatureValue 'RSA_SHA256'
does not match the expected value : 'RSA_SSA_PSS_SHA256_MGF1'. Conversion is not supported!
```

Consequences for the plan:

- The headline #255 case (PSS-only software certificate) **needs no code** —
  `setSigningCertificate` puts `RSASSA_PSS` on the parameters, the token's
  `forKey(privateKey)` agrees, and `SHA256withRSAandMGF1` resolves against the
  registered BC provider (whose defaults are MGF1/same-digest/salt=digest-length/
  trailer 1). It needs a regression test and a doc line, nothing more.
- The real defect is shape 2: parameters and token derive the algorithm from two
  different places. Driving the token from `parameters.getSignatureAlgorithm()`
  (§5) fixes it.
- Still genuinely new: forcing PSS on a plain `rsaEncryption` key (the escape
  hatch), and the PKCS#11 JCE-name/provider path — which shape 1 does *not*
  cover, since it resolved to BC with a software key.

### 1. Model: `SignatureAlgorithm`

New enum in `engines/api/.../types/`, alongside `HashAlgorithm`:

```java
public enum SignatureAlgorithm {
    AUTO,        // derive from the signing certificate / key (default)
    RSA,         // RSASSA-PKCS1-v1_5
    RSASSA_PSS,  // RSASSA-PSS with MGF1, salt length = digest length
    ECDSA;
}
```

- `AUTO` preserves today's behaviour for every existing user.
- `ECDSA` exists so the resolved algorithm is always nameable in logs/errors and
  an EC user can assert intent; not a new feature.
- `BasicSignerOptions.signatureAlgorithm` with the usual
  getter/setter/`loadOptions`/`storeOptions`/`copy`/`equals`/`hashCode`, persisted
  under `Constants.PROPERTY_SIGNATURE_ALGORITHM`.

### 2. Resolution: `SignatureAlgorithms.resolve(...)`

New pure helper in `engines/api/.../utils/`:

```java
public static SignatureAlgorithm resolve(SignatureAlgorithm requested, X509Certificate cert, PrivateKey key)
```

Detection on the **subject public key** algorithm:

| `cert.getPublicKey().getAlgorithm()` | resolved |
|---|---|
| `RSASSA-PSS` | `RSASSA_PSS` |
| `RSA` | `RSA` |
| `EC` / `ECDSA` | `ECDSA` |
| anything else | error naming the algorithm |

- `"RSASSA-PSS"` is what the JDK (11+) returns for a `SubjectPublicKeyInfo`
  carrying `id-RSASSA-PSS` — the wire marker of a PSS-only certificate, the case
  #255 describes.
- The private key is inspected too: cert and key can disagree (PKCS#11 keys
  commonly report `"RSA"` under a PSS-only certificate). Report the conflict
  explicitly rather than letting DSS fail at `ensureSignatureValue`.
- `requested != AUTO` validates rather than overrides: `RSA`/`RSASSA_PSS` against
  an EC key, or `ECDSA` against an RSA key, is a hard error naming both.
- The one allowed disagreement: `RSASSA_PSS` requested against a plain
  `rsaEncryption` certificate — the escape hatch for a CA that mandates PSS
  without marking the key. RFC 4055 permits it, and DSS's `isEquivalent()` accepts
  it.
- Resolved value logged at INFO before signing.

### 3. CLI, GUI, config

```
-sa,--signature-algorithm <auto|rsa|rsassa-pss|ecdsa>
```

- Mirrors `-ha/--hash-algorithm` (`Constants.java:316`); `-sa` is free.
- Default `auto`. Parsed in `SignerOptionsFromCmdLine` with the case-insensitive
  enum handling used for `--pades-level`; accepts `rsassa-pss` and `rsassa_pss`.
- GUI: combo box next to the hash-algorithm control, JavaFX
  (`SigningOptionsViewModel` + FXML) and Swing. Disabled when the active engine
  lacks `SIGNATURE_ALG_RSASSA_PSS`, as the FX UI already does for other
  engine-unsupported controls.
- New keys in `engines/api/.../translations/messages.properties`:
  `hlp.signatureAlgorithm`, `gui.signatureAlgorithm.label`,
  `jfx.gui.signatureAlgorithm.label`, `console.signatureAlgorithm.resolved`,
  `console.signatureAlgorithm.mismatchKey`,
  `console.signatureAlgorithm.unsupportedEngine`. Non-English via Weblate.

### 4. Capability gating — two stages

New `Capability.SIGNATURE_ALG_RSASSA_PSS` in the signature-container group,
declared by `DssSigningEngine` only.

`EngineMismatchValidator.findMismatches()` runs at `SignerLogic.java:84`, before
any keystore is opened, so gating happens twice:

1. **Explicit request, pre-keystore.** New check next to the TSA/OCSP ones:
   `getSignatureAlgorithm() == RSASSA_PSS && !caps.contains(SIGNATURE_ALG_RSASSA_PSS)`
   → standard engine-mismatch message, no PIN prompt.
2. **Auto-detected, post-keystore.** The OpenPDF engine checks the resolved
   algorithm once it has the chain and fails with
   `console.signatureAlgorithm.unsupportedEngine` ("re-run with `-eng dss`").

Actual OpenPDF failure modes without the gate:

- software PSS-only key → `privKey.getAlgorithm()` is `"RSASSA-PSS"` →
  `NoSuchAlgorithmException("unknown.key.algorithm.1")`, i.e. already fails, with
  an unhelpful message;
- PKCS#11 key reporting `"RSA"` under a PSS-only cert → silent PKCS#1 v1.5 bytes
  that validators reject — the bug #255 reports.

The gate replaces the first message and prevents the second.

### 5. DSS engine implementation — token half DONE

Implemented (`DssPssSigningTest` pins all three shapes):

- `PrivateKeyEntryImpl` implements `DSSPrivateKeyAccessEntry`; the
  `sign(ToBeSigned, DigestAlgorithm, ...)` override is gone, so
  `AbstractSignatureTokenConnection` supplies the PSS parameters.
- `DssSigningEngine` calls
  `token.sign(dataToSign, parameters.getSignatureAlgorithm(), token.getKeyEntry())`
  — previously the digest-only overload with a `null` key entry. This is the
  shape-2 fix.
- `getSignatureInstance(String)` overridden: PSS requested under the portable
  `RSASSA-PSS` name, falling back to DSS's `SHAxxxwithRSAandMGF1` if absent; the
  key's own provider is selected explicitly when it offers the algorithm, so an
  opaque PKCS#11 key stays on its provider.
- `PrivateKeyInfo` carries `KeyStore.getProvider()`, set in
  `KeyStoreUtils.getPkInfo`. Null-safe: for JKS/PKCS12 the provider (SUN) does
  not offer `RSASSA-PSS`, so the lookup falls through to normal JCA selection.

Still to do (only needed for the deferred `--signature-algorithm` option):
forcing PSS on a plain `rsaEncryption` certificate, i.e. the
`setEncryptionAlgorithm` call below.

### 5b. Forcing PSS (deferred with the CLI option)

**`DssSigningEngine` parameters** — order matters, `setSigningCertificate`
overwrites the encryption algorithm:

```java
parameters.setDigestAlgorithm(digestAlgorithm);
parameters.setSigningCertificate(...);
parameters.setCertificateChain(...);
if (resolved == SignatureAlgorithm.RSASSA_PSS) {   // AFTER setSigningCertificate
    parameters.setEncryptionAlgorithm(EncryptionAlgorithm.RSASSA_PSS);
}
```

`AUTO`-resolved `RSA`/`ECDSA` keep today's behaviour. Mapping lives in
`DssMappings` with the other model→DSS translations.

**Content size.** `estimateContentSize()` (line 469) needs no change: a PSS
signature value is the same length as PKCS#1 v1.5 for a given modulus, and
`RSASSA-PSS-params` costs ~50 bytes against a reservation padded by kilobytes.
`engine.dss.retryOnUndersize=true` covers the pathological case.

**Token without `CKM_RSA_PKCS_PSS`** throws from `initSign`/`setParameter` →
signing failure naming the token and algorithm, never a silent downgrade.

### 6. TSA nonce (#33) — DONE

- `DssSigningEngine.buildTspSource()` sets `new SecureRandomNonceSource()` when
  `engineConfig.getBoolean(KEY_TSA_NONCE, true)` (`engine.dss.tsa.nonce`, matching
  the existing engine-scoped prefix). `NonceSource` /`SecureRandomNonceSource` come
  from `eu.europa.esig.dss.service`, the artifact `OnlineTSPSource` is already in.
- `OnlineTSPSource` validates the echo in `timeStampResponse.validate(...)`.
- `EmbeddedTsaServer` grew `getLastRequestNonce()` and `echoWrongNonce(boolean)`;
  `DssTsaNonceTest` covers nonce-by-default, opt-out, and rejection of a response
  echoing a different nonce (`TSPValidationException: response contains wrong
  nonce value`).
- Documented in `advanced.default.properties`, the guide's engine-key table, and
  the 3.2.0 release notes.
- OpenPDF's nonce stays hardcoded in `TSAClientBouncyCastle.getTimeStampToken()`.
  The method is `protected`, but honouring the key there means reimplementing the
  whole request/response body to drop one `BigInteger`. Not worth it for a TSA we
  have never seen; the subclass stays available if a real report arrives.

### 7. EC verification (#23) — DONE, no production code needed

Both engines sign with a self-signed P-256 key (`DssEcSigningTest`,
`OpenPdfEcSigningTest`; keystore generated in-test with BC). #23 is confirmed
fixed by the OpenPDF 3 migration.

The two engines disagree on the SignerInfo `signatureAlgorithm` OID:

| Engine | OID | |
|---|---|---|
| `dss` | `1.2.840.10045.4.3.2` | ecdsa-with-SHA256, what RFC 5753 asks for |
| `openpdf` | `1.2.840.10045.2.1` | id-ecPublicKey (`PdfPKCS7.ID_ECDSA`) |

The openpdf signature still verifies (`PdfPKCS7.verify()`, BC CMS parsing), and
id-ecPublicKey is what the iText-2.1 lineage always wrote, so readers tolerate
it. Strict PAdES validators may not. Not fixed here — noted as an upstream
OpenPDF item, and a reason to recommend `-eng dss` for EC.

Remaining:

- Manual checklist entry for an EC PKCS#11 token (no CI hardware).
- "Supported key types" note in the guide: RSA, RSASSA-PSS (dss), EC.
- Close #23 with a link to the tests.

## Rejected alternatives

- **Patch OpenPDF upstream for PSS.** Correct long-term, but puts a release on an
  upstream review cycle and needs a structural change to the SignerInfo writer
  (parameterised `AlgorithmIdentifier`) at two mapping sites. The gate costs
  nothing if a patch lands: `openpdf` just adds the capability.
- **Hand-write the `PSSParameterSpec` in `PrivateKeySignatureToken`.** Duplicates
  `AbstractSignatureTokenConnection.createPSSParam` verbatim; the base class
  already does it correctly.
- **Use `getJCEId()` unchanged for PSS.** BC-only name, and no-provider
  `getInstance` resolves to `SunRsaSign` — broken on PKCS#11, see "Blocker".
- **Rely on delayed provider selection instead of naming the provider.**
  Empirically false once `setParameter` is called; see the measurement above.
- **Infer PSS from `cert.getSigAlgOID()`.** That is what the *issuer* used, which
  says nothing about the subject key.
- **A combined `--signature-algorithm sha256-with-rsa-pss`.** Conflates digest and
  padding, duplicates `--hash-algorithm`, self-validating option matrix.
