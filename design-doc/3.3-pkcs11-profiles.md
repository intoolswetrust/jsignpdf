# PKCS#11 profiles, detection and a config catalog

| Issue | Ask | Outcome in 3.3 |
|---|---|---|
| [#187](https://github.com/intoolswetrust/jsignpdf/issues/187) | Multiple PKCS#11 providers | Named profiles under `<cfg>/pkcs11/`, explicit `--keystore-provider` selection |
| [#491](https://github.com/intoolswetrust/jsignpdf/issues/491) | PKCS#11 onboarding UX | Fail-soft registration, library file picker, token detection, one labelled keystore entry per profile |

Catalog delivery is split: a **bundled, read-only** catalog ships in 3.3; **online refresh** and **community submission/rating** are deferred (§9, §10).

Status: proposal. Target release: 3.3.0.

## Premises (verified in code)

- Registration is single-file and static: `PKCS11Utils.registerProvidersFromDefaultLocation()` reads exactly `<cfg>/pkcs11.cfg` into two static fields (`SUN_PROVIDER`, `JSIGN_PROVIDER`). `Signer.java:134` calls it before the GUI starts.
- **Selection is by keystore *type* string, which cannot distinguish two tokens.** `KeyStoreUtils.getKeyStores()` returns `Security.getAlgorithms("KeyStore")` — a type list. Every SunPKCS11 provider contributes the same `PKCS11` type. `PKCS11Utils.getProviderNameForKeystoreType(type)` returns the *first* provider that supports it.
- **Key listing and loading ignore the provider entirely.** `KeyStoreUtils.loadKeyStore()` (`:324`) calls `KeyStore.getInstance(aKsType)` with no provider, so JCE provider order decides. Only `OpenPdfSigningEngine:409` passes a provider name, and only for the signature.
- Registration is not fail-soft in effect: `initPkcs11Provider` catches `Throwable`, but a bad `library=` path surfaces as a `SEVERE` log plus a silently non-functional keystore entry, and the FX window shows nothing (#491.3).
- SunPKCS11's config parser rejects unknown keywords, so JSignPdf metadata cannot live as extra keys in a `.cfg` file.
- The provider name SunPKCS11 registers is `SunPKCS11-<cfg name=>`. Two profiles with the same `name=` collide.
- `ConfigLocationResolver` already owns `<cfg>` and has `getPkcs11ConfigFile()`; `getPluginsDir()` exists but is JPX-codec-only and is unrelated.
- Preferences → PKCS#11 tab is a single textarea bound to that one file (`PreferencesController:282`).

## Goals

- Several tokens usable in one run, selectable in GUI and CLI, without editing files.
- A wrong or missing driver never prevents the GUI from starting, and always produces a visible reason.
- First-time users find their token without knowing what a `.so`/`.dll` path is.
- Config data stays plain text and hand-editable.

## Non-goals

- No bundled or downloaded PKCS#11 drivers, ever (§8).
- No JSignPdf-operated backend, account system or vote store (§10).
- No auto-application of catalog entries.
- No change to how a token is *used* once selected (signing paths are untouched).

## 1. Profile model

```
<cfg>/
  pkcs11.cfg            # still read, exposed as the profile `default`
  pkcs11/
    certilia.cfg
    yubikey.cfg
```

- Profile id = file stem, sanitized to `[A-Za-z0-9._-]{1,32}`. Files failing the pattern are skipped with a warning.
- Files written by JSignPdf force `name=<id>`; hand-written files are used as-is, and a `name=` that differs from the stem is a warning, not an error. Duplicate `name=` → the second profile fails soft (§2).
- Legacy `<cfg>/pkcs11.cfg` is **read in place, not migrated** — downgrade to 3.2 keeps working. Trade-off: two locations to document; accepted over a one-shot move that a downgrade cannot undo.
- JSignPdf metadata rides in comments so SunPKCS11's strict parser still accepts the file:

```
#jsignpdf:label=Certilia (Croatian eID)
#jsignpdf:provider=sun
#jsignpdf:catalog=hr-certilia@3
name=certilia
library=/usr/lib/pkcs11/libcertilia-pkcs11.so
slotListIndex=0
```

- `provider` ∈ `sun` (default) | `jsign` | `both`. This replaces the unconditional double registration and answers #491.4: one profile = one keystore entry unless the user asks for both.
- Migration: a saved `ksType` of `JSIGNPKCS11` maps to the `default` profile with `provider=jsign`.

## 2. Registration lifecycle

- `Pkcs11Profiles` (new, `engines/api`, `net.sf.jsignpdf.pkcs11`) discovers, parses, registers and exposes profiles. `PKCS11Utils` keeps its current signatures as thin delegates so the engines do not move.
- Each profile registers independently; every failure is captured as `ProfileStatus{id, state=OK|FAILED|DISABLED, message}` and never propagates. The GUI lists failed profiles greyed out with the reason; the CLI prints them under `--list-keystore-providers`.
- Messages must name the cause, not the stack: missing file, unreadable file, `UnsatisfiedLinkError` → "library architecture does not match this JVM (64-bit)", duplicate name, no slot.
- `unregisterProviders()` iterates all registered profiles; the existing 1 s post-removal sleep is paid once, not per profile.

## 3. Selection

- New option `ksProvider` on `BasicSignerOptions` (persisted as `PROPERTY_KSPROVIDER`), holding a **profile id**, not a JCE provider name.
- CLI: `--keystore-provider` / `kspr` (`ksp` is taken by the password), plus `--list-keystore-providers` / `lkp`. Ignored with a warning when `--keystore-type` is not a PKCS#11 type.
- `KeyStoreUtils.loadKeyStore(type, providerName, file, pwd)` — new overload that calls `KeyStore.getInstance(type, provider)`. All six current call sites route through it. **This is the actual #187 bug fix**; the profile list alone would still load the wrong token.
- `EngineMismatchValidator` reports `--keystore-provider <id>` against `Capability.PKCS11_PROVIDER`.
- Resolution order when `ksProvider` is empty: single OK profile → use it; several → error naming the ids (CLI) or force a pick (GUI). Never silently pick the first.

## 4. GUI

- Keystore-type combo lists one entry per OK profile, labelled `PKCS11 — <label or id>`; failed ones appear disabled with their reason as tooltip (#491.1, #491.3, #491.4).
- Keystore-file picker hidden for PKCS#11 types (#491.5).
- "Load Keys" reports success/failure in the window, not on the console.
- Preferences → PKCS#11 becomes a profile list: add / duplicate / remove / rename, a native file chooser for `library=` filtered per OS (`*.so` / `*.dll` / `*.dylib`), and the raw textarea kept as the advanced view of the selected profile.
- "Detect tokens" and "Add from catalog" buttons (§5, §6).

## 5. Detection

- Walks the catalog's `libraries[]` path patterns for the current OS/arch, expands `~`, `%ENV%`/`$ENV`, and `*` globs, and lists what exists **on this machine**.
- Result is a pick list: "found `/usr/lib/opensc-pkcs11.so` → create profile `opensc`". Creating is explicit.
- Offline, no network, no governance. Highest UX return in this document; it should land even if the catalog work slips.

## 6. Catalog (bundled in 3.3)

One JSON resource in `engines/api`, `net/sf/jsignpdf/pkcs11/catalog.json`, also serving §5.

```json
{
  "schemaVersion": 1,
  "updated": "2026-09-14",
  "entries": [
    {
      "id": "hr-certilia",
      "revision": 3,
      "label": "Certilia (Croatian eID)",
      "vendor": "AKD",
      "infoUrl": "https://www.certilia.com/",
      "minSchemaVersion": 1,
      "libraries": [
        { "os": "linux",   "arch": ["x86_64"], "paths": ["/usr/lib/pkcs11/libcertilia*.so"] },
        { "os": "windows", "arch": ["x86_64"], "paths": ["%ProgramFiles%\\AKD\\*\\certilia-pkcs11.dll"] },
        { "os": "macos",   "arch": ["x86_64", "aarch64"], "paths": ["/Library/Certilia/libcertilia-pkcs11.dylib"] }
      ],
      "config": { "slotListIndex": 0 },
      "provider": "sun",
      "notes": "Log in with the PIN when prompted; the card exposes two slots.",
      "tested": [
        { "os": "linux", "osVersion": "Ubuntu 24.04", "driver": "certilia 1.4.2",
          "jsignpdf": "3.3.0", "reporter": "@handle", "date": "2026-04-11" }
      ],
      "discussion": "https://github.com/intoolswetrust/jsignpdf/discussions/0000"
    }
  ]
}
```

- `config` keys are restricted to an allowlist: `slot`, `slotListIndex`, `description`, `nssLibraryDirectory`, `nssSecmodDirectory`, `nssModule`, `nssDbMode`, `attributes`. `library` and `name` are never taken from `config` — `library` comes from the resolved `libraries[]` match, `name` from the profile id. Unknown keys reject the entry. Hand-written user files are *not* restricted; only catalog-sourced material is.
- `minSchemaVersion` lets a newer catalog carry entries an older client skips instead of failing.
- Applying an entry creates a **draft profile** shown with the resolved absolute path, whether that file exists here, and the entry's notes. The user confirms; nothing is written before that.

### Rating: attestations, not thumbs

`tested[]` records replace a star count. A number aggregated over different OSes, driver versions and card models tells a user nothing, and it is precisely the feature that forces accounts and anti-gaming work. The GUI renders "confirmed on 4 systems, most recently 2026-04 (Fedora 42)". Reactions on the linked discussion can serve as a soft popularity signal later.

## 7. Security rules (binding)

A catalog entry says *load this native library into the signing JVM*. Treat it as hostile input.

- Never ship, download, or link a driver binary. Entries reference vendor-installed paths only; the user installs middleware themselves. Also keeps redistribution licensing out of scope.
- Strict key allowlist (§6); reject rather than pass through.
- Never auto-apply, never mutate an existing profile, never change the active profile from catalog data.
- Any network-fetched catalog must be signature-verified before parsing (§9).
- Show the resolved absolute path in the confirm step — the path is the security-relevant part.

## 8. Deferred: online refresh (3.4+)

- Static signed file (GH Pages or release asset), fetched only on explicit user action, ETag-cached, bundled snapshot as fallback, never blocking startup.
- Detached signature verified against a public key baked into the jar; release step signs the catalog.
- A large share of users run on air-gapped or proxied government/corporate desktops — an unsolicited fetch would be a regression for them. Opt-in, documented, no identifiers in the request.

## 9. Deferred: submission and rating (3.4+)

Delegate the social layer to GitHub instead of operating one.

- "Submit your config" opens a prefilled issue/discussion URL in the browser; the catalog repo is the review queue and `tested[]` entries arrive by PR.
- Reaction counts, if ever shown, are baked in at catalog-build time so the app never calls the GitHub API at runtime.
- "Verified" must be labelled honestly in the UI: structurally reviewed + N reported successes, not "tested by the maintainer" — most entries cannot be reproduced without that country's eID card.

## Rejected alternatives

| Option | Why not |
|---|---|
| JSignPdf-hosted catalog/rating service | Hosting, auth, abuse control, moderation, GDPR for voters, and a shipped endpoint that outlives its maintenance. |
| Sidecar `<id>.properties` for metadata | Two files and two sources of truth per profile; comment-encoded keys survive SunPKCS11's parser at no cost. |
| Index file `profiles.properties` | Same duplication; the filesystem already is the index. |
| Distinguish profiles by keystore type string | JCE gives every SunPKCS11 provider the type `PKCS11`; not expressible. |
| One-shot migration of `pkcs11.cfg` into `pkcs11/` | Breaks downgrade to 3.2 for no functional gain. |
| Ship driver binaries or download links | Licensing, and it turns the catalog into a code-distribution channel. |

## Work breakdown

1. `Pkcs11Profiles` + `ProfileStatus`, discovery, comment metadata parsing, fail-soft registration; `PKCS11Utils` delegates. Closes #491.3.
2. `ksProvider` through `BasicSignerOptions`, CLI (`kspr`, `lkp`), provider-aware `loadKeyStore` overload, validator. Closes #187.
3. FX: profile-aware keystore combo, hidden file picker, Load Keys feedback. Closes #491.1/.4/.5.
4. FX: Preferences profile list + library file chooser. Closes #491.2.
5. `catalog.json` + detection + "Detect tokens" / "Add from catalog".
6. `website/docs/` PKCS#11 chapter; guide, CLI help, release notes.

Steps 1–3 are the release-critical path; 5 can ship with an entry count of one.

## Test plan

- Unit: profile discovery (valid/invalid stems, duplicate `name=`, missing file), comment-metadata parsing, catalog parse + allowlist rejection + `minSchemaVersion` skip, path pattern expansion per OS, legacy `pkcs11.cfg` exposure as `default`, `JSIGNPKCS11` ksType migration.
- Unit: `loadKeyStore` picks the named provider when two providers offer the same type (two dummy `Provider`s, no hardware).
- Integration (optional, skipped when absent): SoftHSM2 as a second token alongside a file keystore — verifies that two profiles register and that key listing hits the selected one.
- Manual: real token on Linux + Windows, a deliberately wrong `library=` path (GUI must start), and a 32-bit DLL on a 64-bit JVM (message must mention bitness).

## Open questions
