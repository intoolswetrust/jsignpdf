# PKCS#11 profiles, detection and a config catalog

| Issue | Ask | Outcome in 3.3 |
|---|---|---|
| [#187](https://github.com/intoolswetrust/jsignpdf/issues/187) | Multiple PKCS#11 providers | Named profiles under `<cfg>/pkcs11/`, explicit `--keystore-provider` selection |
| [#491](https://github.com/intoolswetrust/jsignpdf/issues/491) | PKCS#11 onboarding UX | Lazy fail-soft registration, library file picker, token detection, one labelled keystore entry per profile |

Catalog delivery is split: a bundled, read-only catalog ships in 3.3; online refresh and community submission/rating are deferred (§8, §9).

Status: proposal. Target release: 3.3.0.

## Premises (verified in code)

- Registration is single-file and static: `PKCS11Utils.registerProvidersFromDefaultLocation()` reads exactly `<cfg>/pkcs11.cfg` into two static fields (`SUN_PROVIDER`, `JSIGN_PROVIDER`). `Signer.java:134` calls it synchronously before the GUI starts.
- The two providers register keystore types `PKCS11` (SunPKCS11) and `JSIGNPKCS11` (JSignPKCS11), under provider names `SunPKCS11-<name>` and `JSignPKCS11-<name>`.
- Selection is by keystore type string, which cannot distinguish two tokens. `KeyStoreUtils.getKeyStores()` returns `Security.getAlgorithms("KeyStore")`. Every SunPKCS11 provider contributes the same `PKCS11` type. `PKCS11Utils.getProviderNameForKeystoreType(type)` returns the first provider that supports it.
- Key loading ignores the provider: `KeyStoreUtils.loadKeyStore()` (`:324`) calls `KeyStore.getInstance(aKsType)`.
- Signing uses the type-only lookup: `OpenPdfSigningEngine:409` and `EngineMismatchValidator:206` call `getProviderNameForKeystoreType(ksType)`. DSS takes the provider from the loaded key (`pkInfo.getProvider()`).
- Registration is not fail-soft in effect: `initPkcs11Provider` catches `Throwable`, but a bad `library=` path surfaces as a `SEVERE` log plus a silently non-functional keystore entry, and the FX window shows nothing (#491.3). A driver that crashes or hangs in `C_Initialize` takes the JVM down before the GUI appears.
- SunPKCS11's config parser rejects unknown keywords but accepts `#` comments.
- `ConfigLocationResolver` already owns `<cfg>` and has `getPkcs11ConfigFile()`.
- Preferences → PKCS#11 tab is a single textarea bound to that one file (`PreferencesController:282`).

## Goals

- Several tokens usable in one run, selectable in GUI and CLI, without editing files.
- A wrong or missing driver never prevents the GUI from starting, and always produces a visible reason.
- First-time users find their token without knowing what a `.so`/`.dll` path is.
- Config data stays plain text and hand-editable.

## Non-goals

- No bundled or downloaded PKCS#11 drivers (§7).
- No JSignPdf-operated backend, account system or vote store (§9).
- No auto-application of catalog entries.
- No change to the signing algorithm; engines only resolve the provider through the selected profile.
- No TSA client certificate on a token; the TSA keystore combo and `SSLInitializer` stay type-only.
- No profile management in the Swing GUI.

## 1. Profile model

```
<cfg>/
  pkcs11.cfg            # still read, exposed as the profile `default`
  pkcs11/
    certilia.cfg
    yubikey.cfg
```

- Profile id = file stem, sanitized to `[A-Za-z0-9._-]{1,32}`, compared case-insensitively. Files failing the pattern, stems differing only by case, and `pkcs11/default.cfg` (reserved for the legacy file) are skipped with a warning.
- Files written by JSignPdf force `name=<id>`; hand-written files are used as-is, and a `name=` that differs from the stem is a warning. Duplicate `name=` → the second profile fails soft (§2).
- Legacy `<cfg>/pkcs11.cfg` is read in place, not migrated, so a downgrade to 3.2 keeps working.
- JSignPdf metadata rides in comments:

```
#jsignpdf:label=Certilia (Croatian eID)
#jsignpdf:provider=sun
#jsignpdf:catalog=hr-certilia@3
name=certilia
library=/usr/lib/pkcs11/libcertilia-pkcs11.so
slotListIndex=0
```

- `provider` ∈ `sun` (default) | `jsign` | `both`. `both` yields two keystore entries for the profile, one per type. The JCE provider is resolved from the pair (profile id, keystore type).
- Migration: a saved `ksType` of `JSIGNPKCS11` maps to the `default` profile with `provider=jsign`.

## 2. Registration lifecycle

- `Pkcs11Profiles` (new, `engines/api`, `net.sf.jsignpdf.pkcs11`) discovers, parses, registers and exposes profiles. `PKCS11Utils` delegates to it.
- Startup only parses profile files; no native library is loaded. `Signer.java:134` becomes discovery only.
- A profile registers on first use: Load Keys in the GUI, key listing or signing in the CLI. The CLI registers only the selected profile. `--list-keystore-providers` registers every profile to report its state.
- `KeyStoreUtils.getKeyStores()` adds `PKCS11` / `JSIGNPKCS11` when at least one parsed profile offers that type, since no provider is registered yet.
- Every failure is captured as `ProfileStatus{id, state=NOT_LOADED|OK|FAILED|INVALID, message}` and never propagates.
  - `INVALID`: parse-time problems (bad stem, duplicate `name=`, unreadable file).
  - `FAILED`: registration problems (missing library, `UnsatisfiedLinkError`, config rejected by SunPKCS11).
  - Token-level problems (no slot, token not present, wrong PIN) surface at `KeyStore.load` and are reported by Load Keys, not stored in `ProfileStatus`.
- Messages name the cause: missing file, unreadable file, duplicate name, library architecture mismatch (reporting the JVM's `os.arch`), no slot.
- Profile add, edit, rename or remove in Preferences takes effect immediately: the affected profile's providers are unregistered and it returns to `NOT_LOADED`.
- `unregisterProviders()` iterates all registered profiles; the 1 s post-removal sleep is paid once.

## 3. Selection

- New option `ksProvider` on `BasicSignerOptions` (persisted as `PROPERTY_KSPROVIDER`, also stored in presets), holding a profile id.
- CLI: `--keystore-provider` / `kspr` (`ksp` is taken by the password), plus `--list-keystore-providers` / `lkp`. `--keystore-provider` is ignored with a warning when `--keystore-type` is not `PKCS11` or `JSIGNPKCS11`. `--list-keystore-types` keeps printing each type once.
- `PKCS11Utils.getProvider(BasicSignerOptions)` resolves (ksProvider, ksType) to the registered `Provider`, registering on demand. It replaces `getProviderNameForKeystoreType` in `OpenPdfSigningEngine:409`.
- `KeyStoreUtils.getKeyAliases`, `getKeyAlias` and `getPkInfo` load through `KeyStore.getInstance(type, provider)` using that resolution. This is the #187 bug fix. `getCertAliases(type, file, pwd)` and `SSLInitializer` are unchanged.
- `EngineMismatchValidator` checks the type name (`PKCS11` / `JSIGNPKCS11`) instead of querying a registered provider, and reports `--keystore-provider <id>` against `Capability.PKCS11_PROVIDER`.
- Resolution when `ksProvider` is empty: a single valid profile → use it; several → error naming the ids (CLI) or force a pick (GUI).
- `ksProvider` naming a missing profile (e.g. a preset from another machine): the CLI errors with the id and the available ids; the GUI clears the selection and forces a pick.
- Renaming a profile updates `ksProvider` in the main config. Presets holding the old id fall under the missing-profile rule.
- Swing GUI: honours a saved `ksProvider` and the resolution rules above; it shows no profile selector.

## 4. GUI

- The keystore-type combo lists one entry per profile and type, labelled `PKCS11 — <label or id>` (or `JSIGNPKCS11 — …` for `jsign`/`both`). `INVALID` and `FAILED` profiles appear disabled, with their reason as a tooltip (#491.1, #491.3, #491.4).
- Keystore-file picker hidden for PKCS#11 types (#491.5).
- Load Keys registers the profile if needed and reports success or failure in the window.
- Preferences → PKCS#11 becomes a profile list: add / duplicate / remove / rename, a native file chooser for `library=` filtered per OS (`*.so` / `*.dll` / `*.dylib`), and the raw textarea kept as the advanced view of the selected profile.
- "Detect tokens" and "Add from catalog" buttons (§5, §6).

## 5. Detection

- Walks the catalog's `libraries[]` path patterns for the current OS/arch and lists what exists on this machine.
- Patterns support `~`, `%ENV%` / `$ENV` and `*` globs. Entries may list `%ProgramFiles%`, `%ProgramFiles(x86)%` and Debian multiarch directories (`/usr/lib/x86_64-linux-gnu/`).
- `os.arch` is normalized before matching: `amd64` → `x86_64`, `arm64` → `aarch64`.
- A glob matching several files yields one candidate per file, newest first.
- Result is a pick list: "found `/usr/lib/opensc-pkcs11.so` → create profile `opensc`". Creating is explicit.
- Inside Flatpak, detection offers only the runtime's `p11-kit-proxy.so`, which reaches host tokens through Flatpak's p11-kit forwarding. Host library paths are not supported there; the guide says so.
- Offline, no network. It can land even if the catalog work slips.

## 6. Catalog (bundled in 3.3)

One JSON resource in `engines/api`, `net/sf/jsignpdf/pkcs11/catalog.json`, also serving §5.

```json
{
  "schemaVersion": 1,
  "updated": "2026-09-14",
  "entries": [
    {
      "id": "hr-certilia",
      "revision": 3,
      "label": "Certilia (Croatian eID)",
      "vendor": "AKD",
      "infoUrl": "https://www.certilia.com/",
      "minSchemaVersion": 1,
      "libraries": [
        { "os": "linux",   "arch": ["x86_64"], "paths": ["/usr/lib/pkcs11/libcertilia*.so"] },
        { "os": "windows", "arch": ["x86_64"], "paths": ["%ProgramFiles%\\AKD\\*\\certilia-pkcs11.dll"] },
        { "os": "macos",   "arch": ["x86_64", "aarch64"], "paths": ["/Library/Certilia/libcertilia-pkcs11.dylib"] }
      ],
      "config": { "slotListIndex": 0 },
      "provider": "sun",
      "notes": "Log in with the PIN when prompted; the card exposes two slots.",
      "tested": [
        { "os": "linux", "osVersion": "Ubuntu 24.04", "driver": "certilia 1.4.2",
          "jsignpdf": "3.3.0", "reporter": "@handle", "date": "2026-04-11" }
      ],
      "discussion": "https://github.com/intoolswetrust/jsignpdf/discussions/0000"
    }
  ]
}
```

- `config` keys are restricted to an allowlist, with typed values:
  - `slot`, `slotListIndex`: non-negative integer; at most one of the two.
  - `description`: single line, printable, max 64 chars, no `{`, `}`, `=`, `"`.
- `library` and `name` are never taken from `config` — `library` comes from the resolved `libraries[]` match, `name` from the profile id. Unknown keys or invalid values reject the entry. Hand-written user files are not restricted.
- `minSchemaVersion` lets a newer catalog carry entries an older client skips.
- Applying an entry creates a draft profile shown with the resolved absolute path, whether that file exists here, and the entry's notes. The user confirms; nothing is written before that.
- `tested[].reporter` is optional and included only with the reporter's consent.

### Rating: attestations, not thumbs

`tested[]` records replace a star count. A number aggregated over different OSes, driver versions and card models tells a user nothing, and it forces accounts and anti-gaming work. The GUI renders "confirmed on 4 systems, most recently 2026-04 (Fedora 42)". Reactions on the linked discussion can serve as a soft popularity signal later.

## 7. Security rules (binding)

A catalog entry says load this native library into the signing JVM. Treat it as hostile input.

- Never ship, download, or link a driver binary. Entries reference vendor-installed paths only.
- Strict key allowlist and value validation (§6); reject rather than pass through.
- Never auto-apply, never mutate an existing profile, never change the active profile from catalog data.
- Any network-fetched catalog must be signature-verified before parsing (§8).
- Show the resolved absolute path in the confirm step.

## 8. Deferred: online refresh (3.4+)

- Static signed file (GH Pages or release asset), fetched only on explicit user action, ETag-cached, bundled snapshot as fallback, never blocking startup.
- Detached signature verified against a public key baked into the jar; release step signs the catalog.
- Opt-in, documented, no identifiers in the request; many users run on air-gapped or proxied desktops.

## 9. Deferred: submission and rating (3.4+)

- "Submit your config" opens a prefilled issue/discussion URL in the browser; the catalog repo is the review queue and `tested[]` entries arrive by PR.
- Reaction counts, if ever shown, are baked in at catalog-build time; the app never calls the GitHub API at runtime.
- The UI labels entries as "structurally reviewed + N reported successes", not "tested by the maintainer".

## Rejected alternatives

| Option | Why not |
|---|---|
| JSignPdf-hosted catalog/rating service | Hosting, auth, abuse control, moderation, GDPR for voters, and a shipped endpoint that outlives its maintenance. |
| Sidecar `<id>.properties` for metadata | Two files and two sources of truth per profile. |
| Index file `profiles.properties` | Same duplication; the filesystem already is the index. |
| Distinguish profiles by keystore type string | JCE gives every SunPKCS11 provider the type `PKCS11`. |
| One-shot migration of `pkcs11.cfg` into `pkcs11/` | Breaks downgrade to 3.2. |
| Eager registration at startup | A crashing or hanging driver blocks the GUI; the CLI loads libraries it does not use. |
| Ship driver binaries or download links | Licensing, and it turns the catalog into a code-distribution channel. |

## Work breakdown

1. `Pkcs11Profiles` + `ProfileStatus`, discovery, comment metadata parsing, lazy fail-soft registration; `PKCS11Utils` delegates. Closes #491.3.
2. `ksProvider` through `BasicSignerOptions` and presets, CLI (`kspr`, `lkp`), provider-aware key loading, `PKCS11Utils.getProvider` in `OpenPdfSigningEngine`, validator, Swing resolution. Closes #187.
3. FX: profile-aware keystore combo, hidden file picker, Load Keys feedback. Closes #491.1/.4/.5.
4. FX: Preferences profile list, library file chooser, immediate apply. Closes #491.2.
5. `catalog.json` + detection + "Detect tokens" / "Add from catalog", Flatpak p11-kit path.
6. `website/docs/` PKCS#11 chapter; guide, CLI help, release notes.

Steps 1–3 are the release-critical path; 5 can ship with an entry count of one.

## Test plan

- Unit: profile discovery (valid/invalid stems, case collisions, reserved `default.cfg`, duplicate `name=`, missing file), comment-metadata parsing, legacy `pkcs11.cfg` as `default`, `JSIGNPKCS11` ksType migration.
- Unit: no native library loaded at startup; CLI registers only the selected profile.
- Unit: key loading and `PKCS11Utils.getProvider` pick the named provider when two providers offer the same type (two dummy `Provider`s).
- Unit: missing-profile handling for `ksProvider` from config and presets.
- Unit: catalog parse, allowlist rejection, value validation (newline, `=`, braces, `slot` + `slotListIndex`), `minSchemaVersion` skip, path expansion and arch normalization per OS.
- Integration: SoftHSM2 as a second token alongside a file keystore, installed in `pr-builder.yaml` — two profiles register, key listing and OpenPDF signing hit the selected one.
- Manual: real token on Linux + Windows, a deliberately wrong `library=` path (GUI must start), a 32-bit DLL on a 64-bit JVM, Flatpak with a host token via p11-kit.
