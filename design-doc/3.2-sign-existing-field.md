# 3.2 — Sign into an existing signature form field (#223)

## Goal

Let the user sign an **existing empty signature field** (AcroForm `/FT /Sig` with no `/V`) instead of always
creating a new one. This is the standard multi-signer workflow: a form author pre-places "Signature #1",
"Signature #2", each signer fills their own box.

Today both engines always create a new field — `OpenPdfSigningEngine` calls
`sap.setVisibleSignature(rect, page, null)` and `DssSigningEngine` builds a `SignatureFieldParameters` from
coordinates only. Neither needs new PDF-level code; both libraries already support the target case:

| | sign into existing field | list blank fields |
|---|---|---|
| OpenPDF 3.0.5 | `PdfSignatureAppearance.setVisibleSignature(String fieldName)` | `AcroFields.getFieldNamesWithBlankSignatures()` |
| DSS 6.4 | `SignatureFieldParameters.setFieldId(String)` | `PAdESService.getAvailableSignatureFields(doc[, char[] pwd])` |

Verified against the shipped jars: OpenPDF's `setVisibleSignature(String)` reads `/Rect` and the page from the
field and throws `IllegalArgumentException` for a missing or non-signature field; DSS's `PdfBoxSignatureService`
resolves `fieldId` via `findExistingSignatureField` and rejects missing / already-signed / non-signature fields
with its own messages. So this is plumbing + UX, and it can be delivered for both engines at once — with the
two engine-level traps in [Engine specifics](#engine-specifics), which is where the real work is.

## CLI surface

- **`-sf` / `--sig-field <name>`** (both free today — verified against `Constants`).
- **`-lsf` / `--list-sig-fields`** — prints every signature field of the input PDF with number, name, page,
  rect and signed/blank state, then exits.

Accepted argument forms for `--sig-field`:

| Form | Meaning |
|---|---|
| `MyField` | that exact field name |
| `#N` | the N-th signature field in document order, as numbered by `--list-sig-fields` |
| `auto` | the first **blank** field in document order; error if there is none |

**Resolution precedence, so a field really named `auto` or `#1` stays reachable:** an exact field-name match
always wins. `#N` and `auto` are only interpreted as selectors when no field carries that literal name. The
listing marks such a field (`name shadows the "#N" selector`) so the collision is visible rather than
surprising.

**`#N` numbers all signature fields, blank and signed alike**, so a number does not shift under the signer as
earlier fields get filled. Numbering is *document order*: pages in order, and within a page the order of the
widget in the page's `/Annots`. **Neither library gives this for free** — `AcroFields.getFieldNamesWithBlankSignatures()`
iterates a plain `HashMap` (arbitrary order) and DSS returns AcroForm `/Fields` order — so `PdfExtraInfo`
computes the order itself by walking pages and their annotations. `-lsf` and `--sig-field #N` share that one
implementation, so the numbers a user reads are the numbers they can pass back.

**Strict by default:** a name that does not resolve to an existing blank field is an error whose message lists
the available names. Silently creating a stray new field on a typo is the worse failure mode. Creating a
*named* new field is deliberately out of scope (below).

**Exit codes.** The field checks live in `SignerLogic.signFile()` (see [Semantics](#semantics)), which reports
failure as a `false` return; `Signer.signFiles()` turns that into `EXIT_CODE_ALL_SIG_FAILED` (4), or
`EXIT_CODE_SOME_SIG_FAILED` (3) when other files in the same run signed successfully. There is no path from
`SignerLogic` to `EXIT_CODE_COMMON_ERROR`, and this feature does not add one. `-lsf` is a listing command and
exits `0`, or `EXIT_CODE_CANT_READ_FILE` when the input cannot be opened.

### Multiple input files

Signing accepts several paths and wildcards (`Signer.signFiles`), and `--sig-field` applies to all of them:

- The selector is **re-resolved per input file** — `#2` and `auto` mean "in this file", not "in the first file".
  A shared form template signed in batch is exactly the case that makes this useful.
- A file whose selector does not resolve fails **that file only** and the run continues, consistent with how
  every other per-file failure behaves. The overall exit code follows the 3/4 rule above.
- `-lsf` lists the fields of **every** input path given (wildcards expanded), each block prefixed with the file
  name when there is more than one. It needs an input file, unlike the `-lk` / `-lkt` / `-le` listing commands
  that run before any file handling — so it is handled after file expansion, and with no input path it fails
  with the usual "no command" help.

## Semantics

**The field's `/Rect` wins.** Neither library can relocate an existing widget, so when `--sig-field` is set:

- `-pg/--page` and `--llx/--lly/--urx/--ury` are ignored, with a warning if the user set them; the DSS
  coordinate flip in `configureVisibleSignature` is skipped. **The page is not "geometry" here** — DSS still
  needs it, see [Engine specifics](#engine-specifics).
- Field with a zero-size rect → invisible signature, regardless of `-V`.
- Field with a real rect → the appearance is rendered into it: an author who drew a signature box wants
  something drawn in it.
- All appearance options (`--render-mode`, `--l2-text`, `--img-path`, `--bg-path`, `--font-size`) keep
  working unchanged — only the placement source changes.

**`--sig-field` implies visible.** Rather than teaching each engine and the validator a second predicate,
option resolution sets the visible flag when a field is selected, so `isVisible()` stays the single condition
everywhere downstream. This matters more than it looks: today the *entire* appearance block — including the
`setVisibleSignature` / `configureVisibleSignature` call that attaches the signature to the field at all — sits
behind `if (options.isVisible())` (`OpenPdfSigningEngine:263`, `DssSigningEngine:289`), and
`EngineMismatchValidator:129` gates every visible-signature capability check behind the same flag. Without this
rule, `--sig-field` without `-V` would produce a plain new invisible signature in one place and unvalidated
`--img-path` / `--l2-text` / `--render-mode` handling in another. A zero-size field rect still yields an
invisible signature — that is the field's decision, not the flag's.

**Overwrite mode is rejected, fail-fast.** Incremental append is the default (`DEFVAL_APPEND = true`), so the
common multi-signer case needs no extra flag and this feature works out of the box. `--sig-field` combined
with an *effective* overwrite mode is refused outright — not warned about, and not conditioned on whether the
input happens to be signed yet. Signing into a pre-placed field means preserving the document as its author
built it; a non-incremental rewrite contradicts that, and `OpenPdfSigningEngine` additionally deletes every
*signed* field on that path (`OpenPdfSigningEngine:194-203`; blank ones survive), silently dropping a
co-signer's signature.

Effective mode is `isAppendX()`, not the flag: it is false for an explicit `--overwrite` **and** whenever PDF
encryption is requested, which overrides the flag. The error message must name which of the two applies —
the encryption path is invisible in the command line.

Two notes on how this lands per engine, since the reasoning above is really the OpenPDF one:

- For **DSS the check is already covered** by `EngineMismatchValidator:104`: DSS declares no `OVERWRITE_MODE`,
  so any `!isAppendX()` state is rejected before this feature's check runs. Keep the new check anyway — it is
  the engine-independent statement of intent, and it produces the better message.
- DSS's encryption path (`DssSigningEngine.encryptPdf`, line 587) pre-encrypts the input with PDFBox and
  **refuses a document that already has signatures**; blank fields survive its save. So the "a rewrite drops a
  co-signer's signature" argument is OpenPDF-specific. The refusal still stands for DSS — encryption plus a
  pre-placed field is not a combination worth supporting — but the message should say *encryption*, not imply
  data loss.

**Pre-existing bug this feature must not inherit** (fix separately, or as a first commit here): because
`isAppendX()` returns false whenever encryption is requested, `EngineMismatchValidator:104` already rejects
**DSS + `--encryption password`** today with "`--overwrite` requires `OVERWRITE_MODE`" — even though DSS
declares `ENCRYPTION_PASSWORD` and implements it. That rule should test an explicit overwrite request rather
than `isAppendX()`. Leaving it alone means users hit a wrong message on a path this feature documents.

The `--sig-field` checks are pure option state, so they belong with the other fail-fast validations in
`SignerLogic.signFile()` — beside the `EngineMismatchValidator` / `DssLtTrustPreflight` calls, before any
keystore, PIN or field resolution work.

**Not checked, and deliberately so:** `/Lock` dictionaries on the field and a prior certification signature.
Signing the second field of a document certified `NO_CHANGES_ALLOWED`, or a field locked by an earlier signer,
produces a technically valid signature that validators will nonetheless flag. Detecting that needs a DocMDP /
FieldMDP evaluation neither engine exposes today. Document the limitation in the AsciiDoc guide — it is the
most likely support question this feature generates.

## Model / wiring

1. `Constants` — `ARG_SIG_FIELD`/`_LONG`, `ARG_LIST_SIG_FIELDS`/`_LONG`,
   `PROPERTY_SIGNATURE_FIELD = "visibleSignature.fieldName"` (the `visibleSignature.` prefix matches every
   sibling key: `PROPERTY_VISIBLE_PAGE`, `PROPERTY_VISIBLE_POS_LLX`, …), `DEFVAL_SIG_FIELD = null`.
2. `BasicSignerOptions` — `sigFieldName` property, loaded/stored next to `PROPERTY_VISIBLE_*` and copied in
   the clone path (three call sites, same shape as `page`: load ~line 174, store, `copy` ~line 1354).
3. `SignerOptionsFromCmdLine` — register + parse both options; handle `--list-sig-fields` in `Signer` after
   input-file expansion (see [Multiple input files](#multiple-input-files)).
4. `PdfExtraInfo` — new `List<SignatureFieldInfo> getSignatureFields()` (number, name, page, rect, signed
   flag) plus `resolveSignatureField(String selector)`; it already opens the PDF for page geometry, and it
   feeds the listing command, the resolution logic and the GUI. Unlike the existing methods it must **report**
   failures instead of swallowing them into `-1` / `null` — the listing command needs to distinguish "no
   signature fields" from "could not open the file" — and it must honour `getPdfOwnerPwdStrX()` for encrypted
   inputs.
5. Engines — each maps the resolved name to its own call and skips its rectangle computation; see
   [Engine specifics](#engine-specifics) for what is *not* skippable.
6. `Capability.SIGN_EXISTING_FIELD` — declared by both bundled engines, plus a rule in
   `EngineMismatchValidator.findMismatches` (`sigFieldName != null && !caps.contains(...)`) and a message key;
   the FX control disabling then follows from the existing `EngineCapabilities.gate` plumbing.

**Layering:** `PdfExtraInfo` lives in the `jsignpdf` module and the engines depend only on
`jsignpdf-engine-api`, so no engine can call it. Resolution therefore happens in `SignerLogic` before
`engine.sign()`, and the engines receive an already-resolved literal field name through `BasicSignerOptions` —
never `#N` or `auto`.

## Engine specifics

**DSS: set the page.** `PdfBoxSignatureService.signDocumentAndReturnDigest` calls
`SignatureOptions.setPage(fieldParams.getPage() - 1)` *unconditionally*, after `findExistingSignatureField`,
and `SignatureFieldParameters.page` defaults to `1`. The appearance rect does come from the existing widget
(`AbstractPdfBoxSignatureDrawer.getExistingSignatureFieldToFill()` → `widget.getRectangle()`), so the rect part
of "the field wins" holds — but a field on page 3 signed with the default page builds its visual template
against page 0. So the DSS engine must resolve the field's page (PDFBox: the page owning the widget) and call
`fieldParams.setPage(page)` alongside `setFieldId(name)`. This is the first thing to prototype; the test with a
field on page 3 exists to catch exactly it.

**OpenPDF: nothing extra.** `setVisibleSignature(String)` takes the rect and the page from the field itself
(`Item.getMerged(0)` / `Item.getPage(0)`) and applies the page rotation via `getPageRotation` /
`getPageSizeWithRotation`, so rotated pages need no handling on our side. For a field with several kid widgets
it uses widget 0, and so does DSS; the listing must report that same widget's page and rect so the three agree.
A multi-widget signature field is pathological anyway — document the choice, do not engineer around it.

**Field flags.** Hidden / `NoView` widgets are listed (with the flag shown) and can be signed: an invisible
pre-placed field is a legitimate authoring choice, and refusing it would be a new failure mode. An existing
`/AP` or `/DA` on the field is overwritten by the generated appearance — both libraries do this already.

## GUI

Signature settings gets a **"Signature field"** combo: `(create new field)` + the blank fields of the loaded
PDF, populated from `PdfExtraInfo`. Selecting a field disables the page/position controls and the preview's
drag handles, and highlights the field rect in `SignatureOverlay`. The combo is disabled when the active
engine lacks the capability.

**The selection is cleared when the input file changes.** `sigFieldName` is persisted in the properties store
like every other option (and like `PROPERTY_INPDF` itself), which means a name chosen once would otherwise
follow the user to the next, unrelated PDF and hard-fail there under strict resolution. Clearing on file change
in `MainWindowController` keeps the GUI honest; for the CLI the same stickiness applies to a `-lp` properties
file, and the AsciiDoc guide calls it out.

**The legacy Swing UI is not wired.** `SignPdfForm` / `VisibleSignatureDialog` remain only as the JavaFX
fallback path in `Signer.launchGui`; they get no field combo. A field name loaded from a properties file is
carried through unchanged by the Swing dialogs, so nothing breaks — it just cannot be edited there.

## Testing

- `PdfExtraInfo`: document-order numbering (a fixture whose `/Fields` order differs from page order),
  resolution of name / `#N` / `auto`, no blank fields, already-signed field, a field literally named `auto`
  and one named `#1` (precedence), unreadable and password-protected inputs.
- Per engine, a fixture PDF with two blank fields: signing into the second leaves the first blank, output
  validates, and the appearance lands inside the field rect (not at the configured coordinates).
- **Field on page 3** — guards the DSS `setPage` trap; assert the appearance is on page 3 and page 1 is
  untouched.
- Rotated page; zero-size rect → invisible signature; input with no signature fields at all.
- `--sig-field` without `-V` → visible appearance in the field (the implies-visible rule), and the
  capability mismatch checks for `--img-path` / `--l2-text` still run.
- Position options + `--sig-field` → warning, field geometry still used.
- Signed input, default (append) mode → both signatures verify. `--sig-field` with `--overwrite`, and with
  encryption requested, → refusal in both cases, on an *unsigned* input too, and before any keystore access.
- Batch: two input files, `--sig-field #2` re-resolved per file; one file lacking the field fails alone and
  the run exits 3.
- `SignerOptionsFromCmdLineTest`: parsing, persistence round-trip through the properties store.

Fixtures are **generated in the test setup**, not committed: OpenPDF `PdfFormField.createSignature` /
`PdfStamper.addAnnotation` for the two-blank-field and page-3 cases, which keeps the field names, pages and
rects readable next to the assertions and lets the `/Fields`-order-vs-page-order case be built deliberately.
DSS's `PAdESService.addNewSignatureField` is the alternative for a DSS-authored fixture if a cross-library
check is wanted.

## Out of scope

Creating a *named* new field (`--sig-field` never creates), signing several fields in one run, adding empty
signature fields to a PDF (DSS has `addNewSignatureField`, but that is a document-authoring feature, not
signing), and field-level locking (`/Lock`) or DocMDP evaluation — see the limitation note in
[Semantics](#semantics).
