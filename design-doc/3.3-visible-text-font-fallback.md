# 3.3 — Visible-signature font fallback

Issue: [#537](https://github.com/intoolswetrust/jsignpdf/issues/537).

## Goal

- Visible signature text renders in every bundled translation (ja, zh_CN, zh_TW, ta) and for CJK signer names.
- Never produce a visible signature with silently missing characters.

## Findings

- DejaVuSans has no CJK or Tamil glyphs. DSS fails (`No glyph for U+7F72`); OpenPDF silently drops them.
- No usable system font on a stock Linux desktop: Noto CJK ships as CFF `.ttc` (rejected by both engines),
  DroidSansFallback has no ASCII.
- PDFBox (DSS) embeds only TrueType outlines (`glyf`); CFF `.otf` fails. Variable TTFs default to Thin.
- Noto Sans SC Regular (static TTF, Google Fonts) covers Latin, kana and 20 976 of 20 992 basic ideographs,
  so one font serves ja, zh_CN and zh_TW. No hangul.

## Approach

- Bundle `NotoSansSC-Regular.ttf` (10.5 MB) and `NotoSansTamil-Regular.ttf` (79 KB) next to DejaVuSans
  in `engines/api`, OFL licensed.
- `FontUtils.getL2Font(text)`: DejaVuSans if it covers the text, else the first bundled fallback that
  covers all of it. An explicit `font.path` is never replaced.
- `L2Font.missingCharacters(text)`: coverage check via `java.awt.Font.canDisplay`, plus the charset for
  non-Identity encodings (OpenPDF drops characters outside a WinAnsi-encoded font).
- Both engines fail with `console.font.missingGlyphs` when the chosen font does not cover the text.
- DSS embeds a font subset (`DSSFileFont.setEmbedFontSubset(true)`); full embedding adds ~10 MB per signature.
- The JavaFX preview resolves the font from the previewed text, like the engines.

## Trade-offs

- Japanese text uses Simplified Chinese glyph forms for some ideographs; one 10.5 MB font instead of three.
- Korean (hangul) is not covered; such text fails with a clear message, `font.path` is the way out.
- Text mixing CJK and Tamil fails (single font per signature).
