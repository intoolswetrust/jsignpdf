# 3.2 — Append-only document timestamp (#141)

## Goal

Append an ETSI.RFC3161 **DocTimeStamp** revision to a PDF without producing a new signature and without any
private key. Two user cases from the issue:

- Timestamp a document that carries no timestamp of its own (signed or not).
- Periodic archival refresh ("digital continuity"): re-timestamp before the previous archive timestamp's TSA
  certificate expires, so an LTA signature stays verifiable indefinitely.

Closes the remaining part of #141 — `-eng dss -pl LTA` already produces an archive timestamp *at signing time*
(#422); what is missing is doing it to a document that is already on disk.

## Two DSS calls, not one

`PAdESService.timestamp(DSSDocument, PAdESTimestampParameters)` (dss-pades 6.4) is a thin wrapper over two
steps:

1. `PAdESExtensionService.incorporateValidationData()` — writes a DSS-dictionary revision with fresh validation
   data for the signatures/timestamps already in the document. It returns the document unchanged (logging why)
   when there is nothing to collect for: no signatures and no detached timestamps, or signatures without a
   T-level.
2. `PAdESTimestampService.timestampDocument()` — appends the DocTimeStamp revision.

**The engine calls the two steps itself rather than `timestamp()`**, because step 1 is not as forgiving as it
looks. `incorporateValidationData` analyses the document with `CompleteValidationContextExecutor`, which runs
the full alerter:

```java
validationAlerter.assertAllTimestampsValid();
validationAlerter.assertAllRequiredRevocationDataPresent();
validationAlerter.assertAllPOECoveredByRevocationData();
validationAlerter.assertAllSignaturesAreYetValid();
validationAlerter.assertAllSignaturesNotExpired();
validationAlerter.assertAllSignatureCertificatesNotRevoked();
validationAlerter.assertAllSignatureCertificateHaveFreshRevocationData();
```

`CommonCertificateVerifier` defaults `alertOnInvalidTimestamp`, `alertOnMissingRevocationData`,
`alertOnRevokedCertificate`, `alertOnExpiredCertificate` and `alertOnNotYetValidCertificate` to
`ExceptionOnStatusAlert`, and `allRequiredRevocationDataPresent()` walks every chain up to the first
trusted-or-self-signed certificate and demands revocation data for everything below it. So on exactly the input
this feature exists for — someone else's archived document, whose signer certificate has expired (that is *why*
it is archived) and whose chain is not anchored in our trust config — `timestamp()` throws `AlertException`
before a single byte is appended. `JSignPdf` only downgrades those alerts today when
`engine.dss.trust.allowUntrusted=true` (`DssTrustConfigurer#relaxTrustAndRevocationAlerts`), which is a
signing-path opt-in.

Both halves are public API in 6.4, so:

```java
DSSDocument extended = document;
try {
    extended = new PAdESExtensionService(verifier, pdfObjFactory)
            .incorporateValidationData(document, parameters.getPasswordProtection());
} catch (AlertException e) {
    // warn, naming the offending certificates via DssUntrustedChainReporter, and timestamp anyway
}
final DSSDocument timestamped = new PAdESTimestampService(tspSource,
        pdfObjFactory.newSignatureTimestampService()).timestampDocument(extended, parameters);
```

**Alert policy for this operation.** The verifier comes from `DssTrustConfigurer.buildVerifier()` as for
signing, then the alerts that judge *someone else's* signature rather than the token we are producing are
downgraded to `LogOnStatusAlert(WARN)`: `alertOnMissingRevocationData`, `alertOnInvalidTimestamp`,
`alertOnRevokedCertificate`, `alertOnExpiredCertificate`, `alertOnNotYetValidCertificate`,
`alertOnNoRevocationAfterBestSignatureTime`, `alertOnUncoveredPOE`. Rationale: a DocTimeStamp makes no claim
about the validity of what is already in the document — it only proves those bytes existed at a point in time.
Failing because an archived signer certificate expired, or because its revocation data cannot be fetched, would
defeat the feature. The relaxation is unconditional here and independent of `engine.dss.trust.allowUntrusted`,
which stays a signing-path knob; each downgraded alert logs what was missing, so a thin DSS dictionary is
visible rather than silent.

Relaxing beats catching: with the alerts as warnings, DSS still embeds every piece of validation data it *could*
collect for the previous archive timestamp, which is the entire point of a refresh. The `catch` is the safety
net for anything that still throws. Other exceptions propagate and fail the operation, as in the signing path.

A single operation then degrades correctly across every input:

| Input | Result |
|---|---|
| unsigned PDF | pure document timestamp; validation-data step returns early ("No signatures or timestamps found") |
| B-level signature (no TSA) | timestamp only; validation-data step returns early (no T-level to anchor it to) |
| T / LT signature | validation data + DocTimeStamp — the document reaches LTA-shaped material |
| LTA signature | validation data for the previous archive timestamp + a fresh archive timestamp = correct chained refresh |
| any of the above, trust/revocation incomplete | warnings naming what is missing; DSS embeds what it could collect (or skips the dictionary), and the DocTimeStamp is appended either way |

**Deliberately not `extendDocument()`.** Verified against the 6.4 sources:

- `PAdESLevelBaselineT.extendSignatures` throws `IllegalInputException("No signatures found to be extended!")`
  on an unsigned input, so it cannot serve the first bullet of the issue.
- `PAdESLevelBaselineLT.extendSignatures` runs `assertSignaturesValid` and
  `assertCertificateChainValidForLTLevel` on the *existing* signatures, which no alert relaxation covers — they
  are hard requirement checks, not alerts.

A strict "upgrade my own B signature to LTA" operation on top of `extendDocument()` stays out of scope; it can
be layered on the same SPI later.

**Inherent to the scheme, worth documenting:** the DocTimeStamp this run appends is itself only covered by
validation data at the *next* refresh. That is how every LTA chain works, not a limitation of the
implementation.

## Scope

In:

- CLI flag, DSS engine implementation, JavaFX toolbar button + menu item, docs, tests.
- Works on unsigned, signed, and already-timestamped input; batch and wildcards unchanged.

Out:

- Multiple TSAs in one invocation. Re-running appends another DocTimeStamp incrementally, so
  `--timestamp-only -ts TSA1 … && --timestamp-only -ts TSA2 …` already yields the multi-jurisdiction result
  asked for in the issue comments. Document the recipe instead.
- Visible timestamp appearance. `PAdESTimestampParameters.setImageParameters` exists, but an archival timestamp
  should not paint on the page.
- `extendDocument()`-based strict level upgrade (above).
- OpenPDF engine. No DocTimeStamp support; it reports the capability as absent.
- Swing GUI (the legacy JavaFX fallback). `SignerLogic.run()` routes through the new `execute()`, but the flag
  is never set there, so its behaviour is unchanged and no Swing control is added.

## CLI surface

```
jsignpdf -eng dss --timestamp-only -ts http://tsa.example/tsa doc.pdf
```

- **`-tso` / `--timestamp-only`** — both free (checked against `Constants`; `-ts` is `--tsa-server-url`). `-tso`
  is unambiguous under commons-cli's `DefaultParser`: an exact short-option match is tried before any long-prefix
  match, so it is not read as `-ts` with the value `o`.
- **`--tsa-server-url` is mandatory** with it; missing URL is a hard error.
- The flag also forces `setTimestamp(true)`. `isTimestampX()` is `advanced && timestamp`, and the TSA plumbing
  (`EngineMismatchValidator`, the engine's TSA branch) hangs off it. `-ts` already sets it when typed on the
  command line, but a TSA URL arriving from an `-lp` properties file — or from the GUI's TSA panel while its
  toggle is off — would not.
- Every existing TSA option applies unchanged: `--tsa-authentication`, `--tsa-user`, `--tsa-password`,
  `--tsa-policy-oid`, `--tsa-hash-algorithm`, `--tsa-cert-file[-type|-password]`, plus the proxy options.
- `--owner-password` is honoured, to open an encrypted input.

**Rejected combinations — checked while parsing, not later.** `SignerOptionsFromCmdLine` tests
`line.hasOption(...)` next to `-tso` and exits with `EXIT_CODE_PARSE_ERR` (1), one message per offending flag:

| Option | Reason |
|---|---|
| `--overwrite` | a DocTimeStamp *is* an incremental revision |
| `--sig-field` | no signature field is filled |
| `--certification-level` | DocMDP is a signature property |

Parse time rather than `SignerLogic` for three reasons: the error names the flag the user actually typed instead
of derived state (`--overwrite` and PDF encryption both clear `isAppendX()`); a properties file reused via `-lp`
that happens to carry a certification level does not trip it, matching the leniency granted below; and the
JavaFX action needs no sanitising of the options copy, because the engine's timestamp path never reads these
settings.

Ignored with a warning (so a reused properties file or preset does not have to be pruned): keystore/key options,
`-V` and the whole appearance group, `--pades-level`, `--reason` / `--location` / `--contact`, `--ocsp` /
`--crl` (validation data collection is driven by the engine's trust config, not these flags), and
`--encryption` / `--encrypted`.

Encryption is in this list rather than the rejected table: the output is an incremental append, so an encrypted
input keeps its existing encryption without any action on our side, and `-e` is documented in the guide as the
flag for working with secured PDFs — a user timestamping a secured document will reach for it. The warning says
the input's existing encryption is preserved and no encryption is added.

**Engine selection — no auto-detection.** `EngineRegistry.resolve()` stays as it is: `--engine`, else the
`engine=` key in `advanced.properties`, else bundled `openpdf`. The operation needs `Capability.DOC_TIMESTAMP`;
when the resolved engine lacks it, fail through the normal `EngineMismatchValidator` path with a message that
names the capability and points at `-eng dss` / the `engine=` key. So the usual invocation carries `-eng dss`
explicitly, or the user configures `dss` as their default engine once. Rationale: an operation silently
overriding the configured engine would be the only such case in the app, and the engine choice also governs
trust config, revocation fetching and output shape — it should stay the user's explicit decision.

**Output naming.** Reuses `--out-suffix` / `--out-directory` / `--out-prefix`. When no suffix is set, fall back
to a **new advanced key `output.suffix.timestamp=_timestamped`** rather than `output.suffix` (`_signed`), which
would be a lie. Since #479/#483 the whole output composition lives on `BasicSignerOptions` — `outSuffix`,
`outPath`, `outPrefix`, resolved by `getOutSuffixX()` and the static
`composeOutFileName(outPath, outPrefix, inFile, outSuffix)` that both `getOutFileX()` and the `Signer` batch loop
call. `outSuffix` is three-state: `null` = "use the default", `""` = "no suffix, keep the input name" (the GUI's
suffix on/off switch), anything else explicit. So the change is one resolution point plus the config plumbing:

- New `AppConfig.defaultTimestampSuffix()` next to `defaultOutSuffix()`, new
  `Constants.DEFAULT_TIMESTAMP_SUFFIX = "_timestamped"`, and an entry in `advanced.default.properties` beside
  `output.suffix` (same "set this to localize the marker" comment style).
- `BasicSignerOptions.getOutSuffixX()` becomes `outSuffix != null ? outSuffix : (timestampOnly ?
  AppConfig.defaultTimestampSuffix() : AppConfig.defaultOutSuffix())`. `Signer.signFiles()` (the batch path)
  already passes it into `composeOutFileName`.
- `getOutFileX()` passes the raw field (`composeOutFileName(outPath, outPrefix, getInFile(), outSuffix)`); switch
  it to `getOutSuffixX()`, which covers the `-lp` / `-i -o` single-file path. `composeOutFileName` stays static
  and flag-unaware — the FX side passes the suffix it wants explicitly (see below).
- No `outSuffixSet` flag and no getter override in `SignerOptionsFromCmdLine` (which no longer holds the suffix,
  output directory or prefix at all): `-os` is the only writer on the CLI, so "not given" is already observable
  as `null`, and `-tso`/`-os` ordering is irrelevant.

Resulting precedence: explicit `-os` (or the GUI *Output suffix* field / switch) → a suffix loaded from `-lp`, a
preset or `config.properties` (key `outpdf.suffix`, persisted since #479) → `output.suffix.timestamp` → never
`output.suffix`. A `_signed` remembered from the previous signing session therefore wins over `_timestamped`;
that follows the "explicit beats default" rule the field already has, and the user can clear it. `--out-directory`
/ `--out-prefix` (`outpdf.path` since #483) apply unchanged.

An empty suffix — `-os ""`, or the GUI switch turned off — keeps the input name, so with `-tso` and no output
directory the output *is* the input; `SignerLogic.validateInOutFiles` rejects that, and in the GUI the status-bar
output label already flags the collision with its `⚠` warning state (#483) before the button is pressed.

Not exposed in the Preferences dialog. `output.suffix` gained an *Output file suffix* field there in #479, but a
second field for one operation would clutter the *General* tab — file-editable key only, like `buffering.mode`.

Exit codes: the parse-time rejections above exit 1; otherwise unchanged — per-file failure, 3 when some files
succeeded, 4 when none did.

## SPI change

`engines/api`:

```java
// Capability
DOC_TIMESTAMP,   // append-only ETSI.RFC3161 document timestamp, no signature

// SigningEngine
/**
 * Appends a document timestamp to the file described by {@code options}, without creating a signature.
 * Only called on engines declaring {@link Capability#DOC_TIMESTAMP}.
 */
default boolean timestamp(BasicSignerOptions options, EngineConfig engineConfig) {
    throw new UnsupportedOperationException();
}
```

A default method keeps `OpenPdfSigningEngine` and any third-party engine source-compatible.

`BasicSignerOptions`: `boolean timestampOnly` + accessors, copied in `createCopy()`. **Not** added to
`loadFromStore` / `storeToStore` — it is an action, not a setting, so it must not survive in
`config.properties` or a preset.

`SignerLogic`: the in/out validation, engine resolution and capability check are shared, only the terminal call
differs. Add a `public boolean execute()` that dispatches on the flag; keep `signFile()` meaning "sign" and add
`timestampFile()`. `Signer.signFiles()`, `SigningService` and `run()` call `execute()`. The timestamp path skips
`validateSigField()` / `resolveSigField()` (no field is filled) and `DssLtTrustPreflight` (no PAdES level is
requested, and missing trust material now degrades to warnings rather than failing).

`EngineMismatchValidator`: with the flag set, run a small timestamp-oriented table (`DOC_TIMESTAMP`, `TSA`,
`TSA_POLICY_OID`, `TSA_BASIC_AUTH`, `PROXY_SUPPORT`) instead of the sign table — otherwise every
visible-signature and keystore mismatch would fire on options the operation ignores. The TSA sub-entries hang
off `timestampOnly` directly rather than off `isTimestampX()` as the sign table does: here the flag is the
umbrella.

## DSS engine implementation

`DssSigningEngine.timestamp()` reuses the signing path's infrastructure: `buildProxyConfig`,
`DssTrustConfigurer.buildVerifier`, `CapturingTspSource`, `JSignPdfPdfObjFactory`, the `BufferingMode` /
`TempFileResourcesHandlerBuilder` handling, `remoteHttpErrorHint`, and `DssUntrustedChainReporter`. Two pieces
need a small refactor first:

- `buildTspSource` currently also assigns the TSA digest onto the three `PAdESSignatureParameters` timestamp
  parameter sets. Split that assignment out so both callers can supply their own target.
- `signWithContentSize`'s undersize retry loop is parameter-type-specific. Extract the loop (reserve → attempt →
  parse required size → grow) over a functional interface so the timestamp path gets the same behaviour and the
  same `engine.dss.retryOnUndersize` / `engine.dss.contentSize` knobs. The timestamp attempt is a single
  `timestampDocument()` call rather than the three-step `getDataToSign` / `sign` / `signDocument`, but the
  failure is identical: both end in `AbstractPDFSignatureService.assertContentSizeSufficient`, which throws the
  `IllegalArgumentException` the existing `with a length [N]` regex already parses. Each retry costs a fresh TSA
  round-trip here too, so `MAX_CONTENT_SIZE_RETRIES` applies unchanged.

`PAdESTimestampParameters` setup:

- `setDigestAlgorithm(...)` from `options.getTsaHashAlgWithFallback()`. **Required**, not optional:
  `TimestampParameters.digestAlgorithm` defaults to `SHA512` and real TSAs reject it (the cartaodecidadao case
  already noted for archive timestamps). Without this the standalone path would silently use a different digest
  than the signing path does.
- `setPasswordProtection(options.getPdfOwnerPwd())` for an encrypted input.
- `setContentSize(...)`: DSS's default is 9472 bytes and the timestamp token carries the whole TSA chain. Seed
  from the shared estimate (TSA allowance + CMS overhead, no signer chain) and let the extracted retry loop
  handle undersize.

Validation data and the alert policy are as described above: relax the seven alerts on the verifier used for
this operation, run `incorporateValidationData` inside a `try`/`catch (AlertException)` that warns (reusing
`DssUntrustedChainReporter` to name the offending certificates, as `sign()` does) and falls back to the
un-extended document, then append the token.

Trust/online behaviour: unlike LT/LTA signing, a missing trust source is **not** fatal here. Log a warning when
`!trustConfigurer.isOnlineEnabled()` explaining that the timestamp is being appended without validation data,
and keep going.

## JavaFX GUI

A separate action, not a mode — the certificate and appearance panels stay untouched and are simply not
consulted.

- Toolbar `btnTimestamp` next to `btnSign`; `Signing > Add timestamp…` (`menuTimestamp`) next to `menuSign`,
  accelerator `Shortcut+T` (free — the menu bar uses `Shortcut+O/S/Shift+S/Q/Comma/EQUALS/MINUS` and `F9`).
- Enabled when a document is loaded **and** the active engine has `DOC_TIMESTAMP` — as **one** binding, not two
  mechanisms. `setDocumentControlsDisabled` assigns `disableProperty` imperatively on the document-controls
  group while `EngineCapabilities.gate()` *binds* it; doing both to the same control throws
  `A bound value cannot be set` at the first document open. `MainWindowController` already keeps the
  `BooleanProperty noDocument` that `setDocumentControlsDisabled` writes and `menuVisibleSig` / `btnVisibleSig`
  bind against (#477), so reuse it: bind `btnTimestamp.disableProperty()` to
  `engineCapabilities.unsupported(DOC_TIMESTAMP).or(noDocument)` and leave the button out of
  `setDocumentControlsDisabled`. Keep `gate()`'s "not supported by the selected engine" tooltip for the
  capability half so the greyed-out button explains itself (as with `SIGN_EXISTING_FIELD`).
- `menuTimestamp` is a `MenuItem`, not a `Control`, so the existing `gate(Control, …)` does not apply: add a
  `gate(MenuItem, …)` overload (disable binding only — `MenuItem` carries no tooltip) fed by the same combined
  binding.
- Matching the no-auto-detection decision above, the GUI does not switch engines either — the user picks `dss`
  in *File > Preferences* (the `engine=` key), and `refreshActiveEngineFromConfig()` already re-enables the
  control without a restart.
- `onTimestamp()` mirrors `onSign()` minus the encryption validation and the LT preflight, plus: the TSA URL is
  mandatory regardless of the `btnTsa` toggle (that toggle means "timestamp the signature I am about to make",
  a different thing) — empty URL expands the TSA pane and reuses the existing `missingTsaUrl` alert.
- Output name: #483 made *Output directory* (`outPath`) and *Output file name* (`outBaseName`) the two editable
  fields, with `signingVM.outFile` a resolved value that `resolveOutputFile()` owns and rewrites on every
  document, suffix, directory or name change; `onSign()` just does `options.setOutFile(options.getOutFileX())`.
  So the timestamp default only applies when the name is derived: if `outBaseName` is blank, compose the output
  on the **options copy** as `BasicSignerOptions.composeOutFileName(outPath, null, inFile, suffix)` with
  `suffix = signingVM.outSuffixProperty().get()` when non-null (`""` from the off switch included) and
  `AppConfig.defaultTimestampSuffix()` otherwise. A typed name or directory wins unchanged.
- Do not write that path back into `signingVM.outFile` — `resolveOutputFile()` owns it and would overwrite it on
  the next field change, and it is persisted as the *signing* output. The completion message names the file
  actually produced. Same `Sandbox` handling as `onSign()`: the `isDocPortalPath` Save dialog, and the
  `hasDirectoryGrant` re-prompt for a fixed output directory (#483).
- `signingVM.syncToOptions(options)`, then on the copy handed to `SigningService`: `setTimestampOnly(true)`
  **and `setTimestamp(true)`** — the view model sets the timestamp flag from the TSA toggle
  (`opts.setTimestamp(tsaEnabled.get())`), and `isTimestampX()` gates the TSA plumbing. Nothing else needs
  clearing: the rejected combinations are parse-time CLI checks, and the engine's timestamp path never reads
  encryption, certification level or sig-field. The service itself just switches to `SignerLogic.execute()`.
- New strings: `jfx.gui.toolbar.timestamp`, `jfx.gui.menu.signing.timestamp`,
  `jfx.gui.status.timestampInProgress`.

## Tests

`engines/dss` (`EmbeddedTsaServer` + `EmbeddedCa` are already in place):

- unsigned PDF → exactly one new revision, subfilter `ETSI.RFC3161`, original bytes byte-identical prefix.
- B-level signature (no TSA) → token appended, no DSS dictionary (the validation-data step returns early).
- sign at T, then timestamp → DSS dictionary present, two timestamp tokens, validation reports LTA-shaped.
- **untrusted signer chain** — sign at T with the embedded CA, then timestamp with that CA *absent* from the
  trust config: the timestamp is appended and the incomplete validation data is a warning. This is the
  regression test for the alert relaxation; without it the operation throws `AlertException`.
- **expired signer certificate** — the same, with a leaf whose `notAfter` is in the past (needs an
  `EmbeddedCa.issueSigningKeyStore` overload taking explicit validity dates). This is the normal state of an
  archived document and trips `alertOnExpiredCertificate` on every real refresh.
- timestamp twice → two DocTimeStamps, page count and content unchanged.
- `tsa.hashAlgorithm` is honoured — assert the message-imprint OID recorded by the embedded TSA, the same way
  `DssTsaNonceTest` inspects the request.
- undersize `/Contents` retry.
- encrypted input opened with `--owner-password`, asserting the output is *still* encrypted — the incremental
  append preserves it, which is what lets `--encryption` be ignored rather than rejected.
- certified input (DocMDP 1, no changes allowed) → still timestamped: DSS skips
  `checkSignatureRestrictionDictionaries` for a document-timestamp layer. Locks in the intended behaviour.
- online disabled → still produces a timestamp, warning logged, no DSS dictionary.

`jsignpdf`:

- `SignerOptionsFromCmdLineTest` — flag parsing; `-tso` is not swallowed as `-ts o`; the flag implies
  `isTimestampX()`; each of the three rejected flags exits 1 naming that flag; an `-lp` properties file carrying
  a certification level does *not* trip the rejection.
- `OutputSuffixResolutionTest` — extend the existing precedence tests with the `timestampOnly` branch:
  `-os` absent falls back to `output.suffix.timestamp`, `-os` present wins over it, `output.suffix` is *not*
  consulted, a suffix loaded from a properties store (`outpdf.suffix`) also wins, and `-op` / `-opre` compose
  the same way as for signing.
- `AppConfigTest` — `defaultTimestampSuffix()` reads the key and falls back to `_timestamped`.
- new `SignerLogic` test — the missing-TSA-URL error, the ignored-with-warning set, and the capability mismatch
  when the resolved engine is `openpdf` (both explicit `-eng openpdf` and the no-`--engine`, default-config
  case) — asserting the message names `DOC_TIMESTAMP` and mentions `dss`.

`fx`:

- `FxTranslationsTest` covers the new keys once the controls carry `%`-keys.
- a Monocle test (pattern of `SignatureSettingsControllerTest`) that loads the window, flips document-loaded and
  the active engine, and asserts no `A bound value cannot be set` — the binding collision above is a runtime
  failure, not a compile error, so nothing else would catch it.
- the GUI output name: with the *Output suffix* field empty the timestamp action targets `…_timestamped.pdf`,
  with it filled the typed suffix is used, with the suffix switch off the input name is kept (and the run is

## Decisions

Settled during review (2026-08-16):

- Option name: **`-tso` / `--timestamp-only`**.
- Output suffix: **new advanced key `output.suffix.timestamp`**, default `_timestamped`, resolved in
  `BasicSignerOptions.getOutSuffixX()` and applied in the GUI only when the *Output file name* field is blank
  (the derived case). Not exposed in Preferences.
- Engine: **no auto-detection** — the user selects the DSS engine per invocation (`-eng dss`) or configures it
  as the default.
- Validation-data alerts: **relax + catch**. The seven "someone else's signature" alerts become warnings for
  this operation, and the extension step is additionally wrapped in `try`/`catch (AlertException)`. Relaxing
  rather than only catching keeps whatever validation data DSS *can* collect for the previous archive
  timestamp — the point of a refresh.
- Rejected combinations: **enforced at CLI parse time** (`EXIT_CODE_PARSE_ERR`), not in `SignerLogic`, so the
  message names the typed flag, `-lp` presets stay usable, and the GUI needs no option sanitising.
- `--encryption` / `--encrypted`: **ignored with a warning**, not rejected — an incremental append preserves the
  input's existing encryption anyway.

Realigned after the 3.2 output-workflow work landed on master (#479 and #483, rechecked 2026-08-29): output
composition moved onto `BasicSignerOptions` (`outSuffix` three-state, `outPath`, `outPrefix`, `getOutSuffixX()`,
`composeOutFileName`), is persisted as `outpdf.suffix` / `outpdf.path` in `config.properties` and presets, and is
edited in the *Signature Properties* panel (directory, file name, suffix switch + field) and Preferences, with
`resolveOutputFile()` owning the resolved `outFile`. The affected parts of *Output naming*, *JavaFX GUI*, *Docs*
and *Tests* were updated; the SPI, CLI, alert-policy and DSS-engine sections were re-checked against master and
still hold (`-tso` free, `Shortcut+T` free, `Signing` menu with `menuSign`, `noDocument` binding,
`buildTspSource` / `signWithContentSize` / `CapturingTspSource` / `DssTrustConfigurer` unchanged).

No open questions remain; the design is ready to implement.
